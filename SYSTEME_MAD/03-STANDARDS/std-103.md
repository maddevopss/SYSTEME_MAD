STD-103 — Base de données

Règle d’or

Les données sont souvent plus précieuses que le code. Elles doivent être conçues, protégées et conservées avec le plus grand soin.

---

Objectif

Définir les principes de conception et de gestion des bases de données afin d’assurer l’intégrité des données, leur sécurité, leurs performances et leur évolutivité.

Une base de données bien conçue constitue le socle d’une application fiable.

---

Pourquoi ce standard existe

Une mauvaise conception des données entraîne rapidement :

* des incohérences;
* des pertes d’information;
* des problèmes de performance;
* une maintenance complexe.

En appliquant des règles communes, nous assurons la pérennité des données et simplifions l’évolution des applications.

---

Niveau de maturité

🟡 Intermédiaire

Toute personne concevant une base de données ou modifiant son schéma doit respecter ce standard.

---

Champ d’application

Ce standard s’applique à :

* toutes les bases de données relationnelles;
* PostgreSQL;
* MySQL;
* SQLite;
* toute base de données utilisée dans un projet MAD DevOps.

---

Règles obligatoires

Concevoir avant de créer

Le modèle de données doit être réfléchi avant le développement.

Les principales entités et leurs relations doivent être identifiées.

---

Garantir l’intégrité

Les contraintes doivent être utilisées lorsque pertinentes :

* clés primaires;
* clés étrangères;
* contraintes d’unicité;
* contraintes de validation.

Les règles métier importantes ne doivent pas reposer uniquement sur le code applicatif.

---

Utiliser les migrations

Toute modification du schéma doit être réalisée à l’aide d’un système de migrations.

Les changements manuels directement en production sont interdits.

---

Éviter les duplications inutiles

Une même information ne doit pas être stockée à plusieurs endroits sans justification.

Lorsque la duplication est nécessaire pour des raisons de performance, elle doit être documentée.

---

Sauvegarder régulièrement

Chaque projet doit prévoir une stratégie de sauvegarde adaptée à son contexte.

Une sauvegarde non testée ne constitue pas une stratégie de reprise.

---

Bonnes pratiques

✔ Utiliser des noms explicites pour les tables et les colonnes.

✔ Normaliser les données lorsque pertinent.

✔ Créer des index adaptés aux requêtes fréquentes.

✔ Utiliser les transactions pour garantir la cohérence.

✔ Prévoir l’évolution du schéma.

✔ Documenter les changements importants via les ADR lorsque nécessaire.

---

Anti-patterns

Mauvais

Créer une table sans clé primaire.

---

Mauvais

Modifier directement la structure en production sans migration.

---

Mauvais

Utiliser une seule colonne pour stocker plusieurs informations différentes.

---

Bon

Concevoir un schéma clair, normalisé, documenté et accompagné de migrations versionnées.

---

Exemples

Une table doit représenter une seule responsabilité métier.

Les relations doivent être explicites et protégées par des contraintes.

Les données critiques doivent être validées autant par la base de données que par l’application.

---

Cas réel MAD DevOps

MADSuite

MADSuite utilise PostgreSQL avec un schéma versionné par migrations.

Les contraintes d’intégrité, les index et les clés étrangères assurent la cohérence des données.

Les décisions importantes concernant le modèle de données sont documentées et les évolutions sont réalisées progressivement afin de préserver la compatibilité.

Les mécanismes d’isolation multi-tenant et les politiques de sécurité contribuent également à protéger les données des clients.

---

Exceptions

Les prototypes ou les preuves de concept peuvent utiliser une structure simplifiée.

Toutefois, avant une mise en production, la base de données doit respecter les principes définis dans ce standard.
