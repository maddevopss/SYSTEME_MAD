STD-104 — Architecture SaaS Multi-tenant

Règle d’or

Un client ne doit jamais pouvoir accéder, directement ou indirectement, aux données d’un autre client. Cette règle ne connaît aucune exception.

⸻

Objectif

Définir les principes d’architecture, d’isolation et de sécurité des applications SaaS multi-tenant développées par MAD DevOps.

La confidentialité des données constitue une responsabilité fondamentale.

L’isolation entre les organisations doit être garantie par l’architecture elle-même et non uniquement par le code applicatif.

⸻

Pourquoi ce standard existe

Dans une architecture multi-tenant, plusieurs organisations partagent une même application et une même infrastructure.

Cette approche offre d’importants avantages en matière de maintenance, de déploiement et de coûts.

En contrepartie, elle impose une exigence absolue : garantir une isolation complète entre les données de chaque organisation.

Une seule fuite compromettrait la confiance envers l’ensemble du système.

⸻

Niveau de maturité

⚫ Expert

Ce standard s’adresse aux architectes logiciels et aux développeurs responsables de la conception ou de l’évolution d’une application SaaS.

⸻

Champ d’application

Ce standard s’applique à :

* toutes les applications SaaS multi-tenant;
* toutes les API;
* tous les services backend;
* les traitements asynchrones;
* les tâches planifiées;
* les WebSockets;
* les intégrations entre services.

⸻

Règles obligatoires

L’organisation est la frontière de sécurité

Chaque requête, chaque traitement et chaque accès aux données doivent être exécutés dans le contexte d’une organisation clairement identifiée.

⸻

L’isolation doit être assurée à plusieurs niveaux

La protection ne doit jamais reposer sur une seule couche.

Elle doit être assurée par :

* l’authentification;
* l’autorisation;
* la logique métier;
* la base de données;
* les politiques de sécurité;
* les tests.

⸻

La base de données est la dernière ligne de défense

Les mécanismes tels que PostgreSQL Row Level Security (RLS) doivent être utilisés lorsque pertinents afin de garantir l’isolation des données, même en cas d’erreur applicative.

⸻

Les traitements asynchrones respectent les mêmes règles

Les jobs, workers et tâches planifiées doivent toujours exécuter leurs opérations dans le contexte de l’organisation concernée.

Aucun traitement global ne doit contourner les mécanismes d’isolation.

⸻

Les communications temps réel sont isolées

Les WebSockets, notifications et événements doivent être limités à l’organisation concernée.

La diffusion globale d’informations métier est interdite.

⸻

Les tests doivent démontrer l’isolation

L’isolation multi-tenant ne doit jamais être présumée.

Elle doit être prouvée par des tests automatisés.

⸻

Bonnes pratiques

✔ Identifier clairement le contexte d’organisation.

✔ Utiliser des politiques RLS lorsque possible.

✔ Journaliser les événements sensibles.

✔ Vérifier systématiquement les accès.

✔ Concevoir les services comme s’ils étaient exposés à des erreurs humaines.

✔ Documenter les décisions importantes dans des ADR.

⸻

Anti-patterns

Mauvais

Faire confiance uniquement au frontend pour limiter l’accès aux données.

⸻

Mauvais

Exécuter un traitement global sans contexte d’organisation.

⸻

Mauvais

Diffuser un événement WebSocket à tous les clients connectés.

⸻

Mauvais

Supposer qu’une requête est sécurisée sans test démontrant l’isolation.

⸻

Bon

Considérer chaque organisation comme un environnement indépendant, même lorsqu’elle partage la même infrastructure.

⸻

Exemples

Une requête doit toujours être exécutée dans le contexte de l’organisation authentifiée.

Les traitements automatisés, les exports, les notifications et les rapports doivent appliquer les mêmes règles d’isolation que les requêtes interactives.

⸻

Cas réel MAD DevOps

MADSuite

Le développement de MADSuite a permis de formaliser plusieurs principes devenus des standards :

* isolation par organisation;
* politiques PostgreSQL Row Level Security (RLS);
* contexte d’exécution partagé entre les services;
* validation systématique des accès;
* isolation des WebSockets par organisation;
* sécurisation des tâches planifiées;
* vérification des traitements asynchrones;
* audits réguliers de sécurité;
* tests automatisés démontrant l’absence de fuite entre organisations.

Ces apprentissages ont renforcé l’architecture globale de l’application et constituent aujourd’hui la référence pour les futurs projets SaaS de MAD DevOps.

⸻

Exceptions

Aucune exception n’est permise concernant l’isolation des données entre organisations.

Toute dérogation représente un risque critique et doit être évitée.
