## 💻 SECTION 1 : LE GUIDE DE RÉFÉRENCE DES COMMANDES (Node, Prisma, tsx, React, Git, DBs)

### 🚀 Node.js & npm (Gestion des Paquets)
* `npm init -y` : Initialise un projet Node.js en créant un package.json par défaut.
* `npm install <paquet>` : Installe une dépendance requise pour l'exécution en production.
* `npm install -D <paquet>` : Installe un paquet requis uniquement pour le développement.

### ⚡ React + Vite (Front-End)
* `npm create vite@latest mon-projet -- --template react-ts` : Crée un nouveau projet React + TypeScript avec Vite.
* `npm run dev` : Lance le serveur de développement local ultra-rapide (généralement sur http://localhost:5173).
* `npm run build` : Compile et optimise l'application pour la production dans le dossier `/dist`.
* `npm run preview` : Lance un serveur local pour tester le build de production généré.

### 🏃 Exécution TypeScript moderne (tsx)
* `npx tsx script.ts` : Compile en mémoire et exécute le fichier TypeScript au vol.
* `npx tsx --watch script.ts` : Exécute en mode surveillance et redémarre au moindre changement (Ctrl+S).

### 🛠️ Framework Backend, Requêtes & Outils de Production
* `npm install express axios dotenv` : Installe le framework web, le client HTTP et le gestionnaire de fichiers `.env`.
* `npm install -D @types/express` : Installe les types requis pour qu'Express soit entièrement typé.
* `npm install zod` : Validation de schéma pour sécuriser tes entrées d'API (coordonnées, contrats).
* `npm install argon2 jsonwebtoken` : Argon2 pour hacher les mots de passe et JWT pour les jetons de session.
* `npm install date-fns` : Outil de manipulation de dates et délais de contrats.
* `npm install -D prettier eslint` : Formatage automatique et analyse statique du code.

### 🧪 Performance, Files d'Attente & Logs Industriels
* `npm install -D vitest` / `npx vitest` : Lance le gestionnaire de tests en mode surveillance (Watch Mode).
* `npm install bullmq ioredis` : Installe la gestion de files d'attente basée sur Redis pour gérer les flux massifs de coordonnées GPS.
* `docker run --name mon-redis -p 6379:6379 -d redis` : Démarre un serveur Redis local en arrière-plan via Docker.
* `npm install pino` / `npm install -D pino-pretty` : Logger JSON ultra-rapide pour remplacer les console.log().

### 🗄️ Écosystème des Bases de Données (SQL, Postgres, MongoDB, Prisma)
* `psql -U <user> -d <db>` : Connecte le terminal à une base de données PostgreSQL locale ou distante.
* `pg_dump -U <user> <db> > backup.sql` : Génère une sauvegarde complète au format SQL.
* `mongosh` : Lance le shell de commande officiel de MongoDB.
* `npx prisma init --datasource-provider postgresql` : Initialise Prisma configuré pour PostgreSQL.
* `npx prisma init --datasource-provider mongodb` : Initialise Prisma configuré pour MongoDB.
* `npx prisma migrate dev --name <nom>` : Crée et applique une migration SQL locale, puis regénère le client.
* `npx prisma db push` : Synchronise le schéma directement avec la base de données sans historique de migration.
* `npx prisma studio` : Lance l'interface utilisateur web locale sur http://localhost:5555.

### 🦀 Programmation Système (Rust + Cargo)
* `cargo new <nom_projet>` : Crée une application Rust binaire complète.
* `cargo check` : Analyse le code à l'aide du compilateur de façon ultra-rapide sans générer de binaire.
* `cargo build --release` : Compile le projet avec les optimisations maximales (target/release/).

### ☕ Environnement Multiplateforme (Java / Maven & Gradle)
* `java Nom.java` : Exécute directement un fichier de code source unique (Java 11+).
* `mvn package` : Package le code avec Maven dans son format de distribution final (.jar).
* `./gradlew build` : Compile, teste et assemble le projet au grand complet avec Gradle.

### 🌿 Gestion de Version (Git)
* `git init` : Initialise un nouveau dépôt Git local.
* `git status` : Affiche l'état des fichiers modifiés ou prêts pour le commit.
* `git add .` : Ajoute toutes les modifications à la zone de staging.
* `git commit -m "Message"` : Enregistre les modifications avec un message descriptif.
* `git checkout -b <branche>` : Crée une branche et bascule dessus instantanément.
* `git push` / `git pull` : Synchronise les commits locaux avec le serveur distant (GitHub).

## 🗺️ SECTION 2 : RECHERCHE GÉOSPATIALE AVANCÉE (GPS Offline & Rendu Voiture)

### 📡 Spécification Mapbox Vector Tile (MVT) & Encodage Protobuf[cite: 1]
* **Standard :** Basé sur le standard de l'OGC, le format Mapbox Vector Tile (MVT) utilise les Protocol Buffers (Protobuf) de Google (`.pbf`)[cite: 1].
* **Performance :** Réduit la taille des fichiers cartographiques de **80 % à 90 %** par rapport au raster[cite: 1]. Le décodage binaire s'exécute à la volée sur le GPU via OpenGL ou Metal, garantissant une fluidité maximale[cite: 1].
* **Look-Ahead Caching :** L'algorithme calcule le vecteur de déplacement $\vec{v}$ et la vitesse pour projeter un cône de trajectoire[cite: 1]. Les tuiles à l'avant sont pré-téléchargées; les tuiles arrières sont purgées selon une stratégie de remplacement spatial de type **Least Recently Used (LRU)**[cite: 1].

### ⚡ Écriture Haute Fréquence (GPS 1 Hz) & SQLCipher[cite: 1]
* **Le coût du chiffrement :** Le chiffrement par blocs AES-256 de SQLCipher ajoute un overhead CPU lourd lors de chaque écriture brute[cite: 1].
* **Stratégie de résilience :**
  1. **Mode WAL :** Forcer impérativement `PRAGMA journal_mode=WAL;` pour autoriser les lectures et écritures simultanées[cite: 1].
  2. **Batching (Transactions groupées) :** Les coordonnées entrantes sont mises en mémoire dans une file d'attente et écrites par blocs (`BEGIN TRANSACTION; ... COMMIT;`) toutes les 30 à 60 secondes[cite: 1]. Cela réduit les requêtes I/O physiques sur le disque par un facteur de 50[cite: 1].

### 🚗 Contraintes Écrans de Véhicules (CarPlay & Android Auto)[cite: 2]
* **Android Auto :** Le rendu doit s'effectuer sur une surface déportée fournie par l'API `SurfaceCallback` d'Android for Cars[cite: 2]. Le rafraîchissement doit être bridé à **30 FPS maximum** sous peine de provoquer une surchauffe thermique du téléphone en mode sans-fil[cite: 2].
* **Apple CarPlay :** Le rendu graphique utilise le framework CarPlay et le modèle `CPMapTemplate`[cite: 2]. Dès que CarPlay est actif, l'application doit complètement geler le rendu de la carte sur l'écran physique de l'iPhone afin de diviser par deux la consommation des ressources du GPU[cite: 2].

## 📐 SECTION 3 : RECHERCHE AVANCÉE EN TÉLÉDETECTION ET CALCUL DE TERRAINS/TOITS

### 📡 Technologie RTK (Real-Time Kinematic) et Précision[cite: 3]
* Le GPS standard de téléphone (marge d'erreur de 3 à 5 mètres) est banni pour les soumissions commerciales[cite: 3].
* Le positionnement cinématique en temps réel (RTK) s'appuie sur une station de base au sol transmettant des corrections différentielles au récepteur mobile (*rover*)[cite: 3]. La précision horizontale passe sous la barre des **1 à 2 centimètres**[cite: 3].
* **Parsing des trames NMEA-0183 ($GNGGA) :** L'application doit parser le flux ASCII brut et analyser la position 6 (Qualité) : `1` = Rejet (GPS standard), `4` = **RTK Fix** (Précision centimétrique verrouillée, seule valeur contractuelle acceptée), `5` = **RTK Float** (Précision décimétrique, mettre l'interface en attente)[cite: 7].

### 📸 Télédétection : Photogrammétrie vs LiDAR[cite: 3]
* **Photogrammétrie (SfM) :** Reconstruction 3D par alignement d'images aériennes prises par drone avec recouvrement de 80%[cite: 3]. Précision de **1 à 3 cm par pixel**[cite: 3]. Échoue dans les zones d'ombres intenses ou sur les surfaces sombres dénuées de contraste[cite: 3].
* **LiDAR (Light Detection and Ranging) :** Émission de pulsations laser calculant le temps de vol (Time of Flight)[cite: 3]. Précision absolue constante inférieure à **2 cm**[cite: 3]. Avantage exclusif : **il traverse la végétation**[cite: 3]. En analysant le dernier écho (last return), le laser ignore les feuilles des arbres pour donner la vraie mesure géométrique du toit ou du sol situé en dessous[cite: 3].

### 📐 Formules Mathématiques du Moteur Géospatial[cite: 3]
* **Aire d'un terrain plat (Polygone 2D) - Formule de l'Arpenteur (Shoelace Formula) :**
  $$A = \frac{1}{2} \left| \sum_{i=1}^{n-1} (X_i Y_{i+1} - X_{i+1} Y_i) + (X_n Y_1 - X_1 Y_n) \right|$$
* **Correction de pente tridimensionnelle pour toitures (Pitch) :**
  Une vue orthogonale satellite 2D donne une surface projetée au sol ($A_{2D}$)[cite: 3]. L'aire réelle en pente ($A_{réelle}$) se calcule avec l'angle de la pente $\theta$[cite: 3] :
  $$A_{réelle} = \frac{A_{2D}}{\cos(\theta)}$$
  *Exemple :* Pour un toit à forte pente de 45° (toit 12/12), le cosinus applique un overhead de **41.4 % de surface réelle supplémentaire**[cite: 3].
* **Toits complexes multi-versants :** Le toit est découpé en facettes triangulaires 3D $P_i(X_i, Y_i, Z_i)$[cite: 7]. L'application calcule le produit vectoriel de deux arêtes ($\vec{AB} \times \vec{AC}$) pour obtenir son vecteur normal unique $\vec{N}(N_x, N_y, N_z)$[cite: 7]. L'aire réelle de la facette se calcule via le produit scalaire avec le vecteur vertical pur[cite: 7] :
  $$A_{réelle} = \frac{A_{2D}}{\frac{|N_z|}{\|\vec{N}\|}}$$

### ☀️ Algorithme d'Analyse d'Ombrage (Raycasting LiDAR)[cite: 7]
* Intégration du *Solar Position Algorithm* (PSA) pour obtenir l'azimut ($\alpha$) et l'élévation ($\in$) du soleil selon les coordonnées GPS et l'heure[cite: 7].
* L'application projette un vecteur (un rayon) depuis chaque mètre carré du modèle numérique de surface vers le soleil[cite: 7]. Si le rayon intersecte un point du nuage LiDAR (toit d'un voisin, arbre), la zone est marquée "à l'ombre"[cite: 7]. Permet de générer une carte thermique (Heatmap) d'ensoleillement cumulé pour le choix des végétaux par le paysagiste[cite: 7].

## 📅 SECTION 4 : MOTEURS DE PLANIFICATION TEMPORELLE ET AGENDAS SÉCURISÉS

### 📄 Standard iCalendar (RFC 5545) & Gestion de la Récurrence[cite: 4]
* Formatage universel obligatoire des flux d'agendas via les spécifications de la **RFC 5545** (balises `VEVENT` pour les rendez-vous et `VTODO` pour les tâches contractuelles)[cite: 4].
* Les règles de récurrence complexes (`RRULE`) doivent être calculées dynamiquement à la volée (*On-the-Fly*) pour la fenêtre d'affichage courante de l'utilisateur à partir d'indexations temporelles en timestamps UTC afin de ne pas saturer la RAM de l'appareil[cite: 4].

### 🤖 Spécificités d'Intégration et Anti-Rejet par Système d'Exploitation[cite: 4]
* **Android :** Accès aux agendas natifs via l'API `CalendarContract`[cite: 4]. Pour déclencher un rappel de délai de contrat à une seconde précise sans que l'OS ne suspende le thread, enregistrement obligatoire dans le `AlarmManager` du système via `setExactAndAllowWhileIdle()`[cite: 4]. Requiert la permission spéciale `SCHEDULE_EXACT_ALARM` (Android 14+), qui doit être rigoureusement justifiée lors de la soumission sur le Play Store sous peine de rejet immédiat[cite: 4].
* **iOS :** Manipulation de l'agenda système via le framework `EventKit` (`EKEventStore`)[cite: 4]. Requiert les clés d'isolation strictes dans le `Info.plist` (`NSCalendarsWriteOnlyAccessLevel` ou `NSCalendarsFullAccessLevel`)[cite: 4]. Les alertes de contrat majeures doivent utiliser les *Time-Sensitive Notifications* via l'entitlement dédié d'Apple[cite: 4].
* **Windows :** Intégration via l'espace de noms natif `Windows.ApplicationModel.Appointments` pour affichage dans le panneau de calendrier de la barre des tâches Windows[cite: 4]. Les calculs d'arrière-plan utilisent un `BackgroundTaskBuilder` configuré avec un `TimeTrigger` (minimum de 15 minutes d'intervalle)[cite: 4].
* **Linux :** Envoi de requêtes IPC via le protocole D-Bus au démon centralisé **Evolution Data Server (EDS)** (`org.gnome.evolution.dataserver.Calendar`) pour intégration à l'horloge centrale du bureau GNOME[cite: 4]. Intégration d'un client HTTP supportant les requêtes `PROPFIND` et `REPORT` pour la synchronisation décentralisée via des serveurs **CalDAV (RFC 4791)**[cite: 4].
* **ChromeOS :** Consommation de la *Google Calendar REST API* via des flux sécurisés OAuth2[cite: 4]. Les minuteurs JS standards échouant lors de la mise en veille du Chromebook, la PWA doit exploiter la `Periodic Background Sync API` pour rafraîchir les fenêtres de délais dès le retour du réseau[cite: 4].

### 🔄 Algorithmes de Résolution de Conflits Hors-Ligne (CRDT)[cite: 5]
* Pour la synchronisation déconnectée sur le chantier, l'application implémente un modèle **LWW-Element-Set CRDT** (Conflict-free Replicated Data Type) basé sur le principe du *Last-Write-Wins*[cite: 5].
* Chaque modification d'horaire possède un UUID et un timestamp de haute précision[cite: 5]. Lors de la reconnexion, la fusion s'effectue de manière autonome[cite: 5]. 
* **Correction de dérive (Clock Skew) :** Les horloges des appareils des employés variant toutes, l'application interroge un serveur de temps via le protocole **NTP** au démarrage, calcule l'offset de dérive local (*Clock Drift Offset*) et corrige le timestamp de l'appareil avant toute opération de fusion CRDT[cite: 5].

### 📡 Gestion Réseau & Chiffrement au Repos des Fichiers de Chantiers[cite: 5]
* **Backoff Exponentiel & Gigue (Jitter) :** En véhicule (CarPlay/Android Auto), l'intercepteur réseau double son délai d'attente à chaque échec de requête de synchronisation (1s, 2s, 4s...) et y ajoute une variable aléatoire (*Jitter*) pour éviter que toute une flotte de camions ne sature le serveur d'API lors du retour du réseau[cite: 5].
* **Chiffrement matériel (iOS) :** Les PDF de contrats signés et photos de toits sont protégés au repos via la clé d'écriture matérielle `NSDataWritingOptions.completeFileProtectionUnlessOpen` gérée par la *Secure Enclave* d'Apple[cite: 5].
* **Chiffrement Android :** Utilisation de l'API `EncryptedFile` (Jetpack Security) qui encapsule les flux de données en AES-256 mode GCM en stockant les clés de façon transparente dans l'**Android Keystore**[cite: 5].
