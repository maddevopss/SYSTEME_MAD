# STD-302 — Revue de code

## Règle d’or

Une revue de code ne cherche pas une personne à blâmer. Elle protège le projet.

---

## Objectif

Définir les principes de revue de code pour maintenir la qualité, la sécurité, la cohérence et la maintenabilité des projets MAD DevOps.

La revue de code sert à améliorer le système avant que les problèmes deviennent coûteux.

---

## Pourquoi ce standard existe

Même une bonne implémentation peut cacher un risque lorsqu’elle est lue seulement sous l’angle technique.

La revue de code ajoute un regard critique sur :

- la logique métier;
- la sécurité;
- la lisibilité;
- la cohérence avec l’architecture;
- les impacts sur les autres modules;
- les tests;
- la documentation;
- la maintenabilité.

---

## Niveau de maturité

🟢 Fondamental

Toute modification importante doit être relue avant d’être considérée prête.

---

## Champ d’application

Ce standard s’applique à :

- code applicatif;
- migrations de base de données;
- routes API;
- jobs asynchrones;
- composants frontend;
- automatisations;
- configuration de déploiement;
- scripts qui modifient des données;
- prompts ou agents IA intégrés dans un produit.

---

## Règles obligatoires

### Comprendre l’intention

La revue doit commencer par comprendre le problème que la modification cherche à régler.

Une correction techniquement valide peut être mauvaise si elle ne répond pas au bon besoin.

### Vérifier les impacts

Chaque modification doit être évaluée selon ses impacts possibles :

- sécurité;
- données;
- performance;
- UX;
- tests;
- documentation;
- compatibilité;
- comportement existant.

### Vérifier les zones sensibles

Une revue doit porter une attention particulière aux zones suivantes :

- authentification;
- autorisation;
- accès aux données;
- multi-tenant;
- paiements;
- exports;
- intégrations externes;
- jobs asynchrones;
- logique qui envoie des emails ou notifications.

### Exiger des tests lorsque nécessaire

Une modification qui touche un comportement critique doit inclure ou mettre à jour les tests pertinents.

### Garder les commentaires utiles

Les commentaires de revue doivent être :

- précis;
- respectueux;
- orientés solution;
- reliés au risque ou à la maintenabilité.

---

## Bonnes pratiques

✔ Relire par petits lots lorsque possible.

✔ Demander le contexte lorsqu’une décision semble étrange.

✔ Vérifier que la correction ne masque pas seulement un symptôme.

✔ Repérer les duplications introduites.

✔ Vérifier les noms de fonctions, variables et modules.

✔ Vérifier si une ADR est nécessaire.

✔ Vérifier si la documentation doit être mise à jour.

✔ Utiliser les agents IA comme assistant de revue, mais ne pas leur déléguer le jugement final.

---

## Anti-patterns

### Mauvais

Approuver parce que le code semble fonctionner localement.

### Pourquoi c’est problématique

La revue doit valider les comportements importants, pas seulement l’absence d’erreur visible.

---

### Mauvais

Faire une revue uniquement stylistique.

### Pourquoi c’est problématique

Le style est important, mais les risques métier, sécurité et données le sont davantage.

---

### Mauvais

Utiliser un ton accusateur.

### Pourquoi c’est problématique

La revue doit renforcer la qualité et la confiance, pas créer une culture défensive.

---

## Exemples

Bon commentaire de revue :

> Cette route touche des données client. Peux-tu confirmer que le contexte d’organisation est appliqué et ajouter un test de refus pour une organisation différente ?

Mauvais commentaire de revue :

> Pas bon.

---

## Cas réel MAD DevOps

Dans MADSuite, une revue de code doit porter une attention particulière à :

- l’isolation par organisation;
- les politiques RLS;
- les jobs de facturation;
- les notifications;
- les WebSockets;
- les paiements Stripe;
- les exports PDF;
- les modules cognitifs qui influencent l’interface.

---

## Exceptions

Un correctif urgent peut être appliqué rapidement pour restaurer un service.

Toutefois, une revue après coup doit être effectuée lorsque le risque est stabilisé.
