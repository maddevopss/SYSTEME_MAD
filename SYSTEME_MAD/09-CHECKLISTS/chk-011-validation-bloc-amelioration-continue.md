# CHK-011 — Validation du bloc amélioration continue MAD DevOps

## Objectif

Valider que le bloc **Amélioration continue MAD DevOps** permet de transformer les irritants, blocages, apprentissages et frictions récurrentes en améliorations utiles, sans créer une surcharge documentaire.

Cette checklist sert à vérifier que le système apprend réellement de l’expérience terrain.

---

## Principe

```text
Observer.
Comprendre.
Corriger.
Documenter.
Améliorer.
Réessayer.
```

---

# 1. Capture des irritants

- [ ] Un irritant peut être noté sans analyse excessive.
- [ ] Un blocage peut être relié à une cause utile.
- [ ] Une friction récurrente peut être conservée.
- [ ] Les opportunités sans suite produisent un apprentissage si pertinent.
- [ ] Les irritants ne deviennent pas automatiquement des projets.

---

# 2. Transformation en amélioration

- [ ] Une friction peut devenir une amélioration proposée.
- [ ] L’amélioration réduit le flou, le risque ou la friction.
- [ ] L’amélioration peut toucher un guide, template, playbook, checklist ou une règle.
- [ ] L’amélioration a une prochaine action claire.
- [ ] Une amélioration trop vague peut être reportée ou abandonnée.

---

# 3. Priorisation

- [ ] Le registre permet de classer les améliorations.
- [ ] L’impact attendu est visible.
- [ ] L’effort estimé est visible.
- [ ] La priorité est visible.
- [ ] Une seule amélioration système par semaine suffit.

---

# 4. Simplicité et anti-usine à gaz

- [ ] Le système ne force pas à tout documenter.
- [ ] Les idées non prioritaires peuvent être reportées.
- [ ] Les idées trop lourdes peuvent être abandonnées.
- [ ] Une amélioration ne doit pas ajouter plus de charge que de valeur.
- [ ] Le pilotage peut être utilisé même quand l’énergie est basse.

---

# 5. Boucle hebdomadaire

- [ ] La routine courte permet de choisir une amélioration réaliste.
- [ ] Le journal de bord permet de conserver un apprentissage.
- [ ] Le registre permet de suivre ce qui est retenu, fait, reporté ou abandonné.
- [ ] La semaine peut se conclure avec une célébration ou un apprentissage.
- [ ] Le système aide à ne pas perdre le fil.

---

# 6. Application réelle

- [ ] Une amélioration issue d’un exemple terrain a été appliquée.
- [ ] Une friction projet peut améliorer un template.
- [ ] Une livraison peut produire un apprentissage.
- [ ] Une opportunité sans suite peut améliorer le parcours client.
- [ ] Une surcharge système peut mener à une simplification.

---

# 7. Indexation

- [ ] Les guides d’amélioration continue sont listés dans `SYSTEME_MAD/02-GUIDE/README.md`.
- [ ] Les templates d’apprentissage et d’amélioration sont listés dans `SYSTEME_MAD/07-TEMPLATES/README.md`.
- [ ] Les checklists de pilotage sont listées dans `SYSTEME_MAD/09-CHECKLISTS/README.md`.
- [ ] Cette checklist est listée dans `SYSTEME_MAD/09-CHECKLISTS/README.md`.
- [ ] Le cockpit fondateur pointe vers les documents d’amélioration continue.

---

# 8. Verdict

## Bloc validé

- [ ] Le bloc capture les apprentissages utiles.
- [ ] Le bloc transforme les frictions en améliorations.
- [ ] Le bloc évite l’accumulation d’idées non traitées.
- [ ] Le bloc reste léger pour un fondateur solo.
- [ ] Le bloc aide le système à évoluer sans se complexifier.

## À ajuster

- [ ] Les apprentissages sont dispersés.
- [ ] Le registre est trop lourd.
- [ ] Trop d’améliorations sont lancées en même temps.
- [ ] Les idées reportées ne sont jamais triées.
- [ ] Le système ajoute de la charge au lieu d’en enlever.

---

## Critère de réussite

Le bloc **Amélioration continue MAD DevOps** est validé s’il permet de répondre rapidement :

```text
Qu’est-ce qui a ralenti ?
Quelle cause utile a été observée ?
Qu’est-ce qu’on garde comme apprentissage ?
Quelle amélioration vaut vraiment la peine ?
Qu’est-ce qu’on reporte ou abandonne ?
Qu’est-ce qu’on simplifie ?
```
