# STD-301 — Stratégie de tests

## Règle d’or

Un comportement critique qui n’est pas testé est un comportement qu’on espère, pas un comportement qu’on maîtrise.

---

## Objectif

Définir les principes de tests applicables aux projets MAD DevOps afin d’améliorer la fiabilité, réduire les régressions et protéger les comportements critiques.

Les tests ne servent pas à prouver que le code existe. Ils servent à démontrer que le système respecte ses promesses importantes.

---

## Pourquoi ce standard existe

Un projet peut fonctionner aujourd’hui et briser demain après une correction mineure.

Les tests permettent de conserver la confiance lorsqu’un projet évolue.

Chez MAD DevOps, les tests doivent protéger :

- la logique métier;
- la sécurité;
- les flux critiques;
- les données client;
- les intégrations importantes;
- les règles multi-tenant;
- les comportements difficiles à vérifier manuellement.

---

## Niveau de maturité

🟢 Fondamental

Tout projet qui devient sérieux doit posséder une stratégie de tests adaptée à son risque.

---

## Champ d’application

Ce standard s’applique à :

- applications Web;
- API;
- SaaS;
- applications desktop;
- applications mobiles;
- scripts critiques;
- intégrations externes;
- modules IA ou automatisés.

---

## Règles obligatoires

### Tester les règles critiques

Les règles métier critiques doivent être couvertes par des tests automatisés.

Exemples :

- calcul de facture;
- droits d’accès;
- isolation multi-tenant;
- conversion devis vers facture;
- paiement;
- génération de document;
- workflow qui modifie des données client.

### Tester les erreurs importantes

Un test ne doit pas seulement démontrer que le bon chemin fonctionne.

Il doit aussi démontrer que le système refuse correctement les cas dangereux.

Exemples :

- utilisateur non autorisé;
- organisation différente;
- donnée invalide;
- état incohérent;
- opération déjà effectuée.

### Prioriser les tests utiles

Tous les fichiers n’ont pas besoin du même niveau de test.

La priorité va aux zones où une erreur pourrait causer :

- perte de données;
- fuite de données;
- erreur financière;
- blocage utilisateur;
- incohérence métier;
- régression difficile à détecter.

### Garder les tests lisibles

Un test doit expliquer un comportement.

Son nom doit permettre de comprendre :

- le contexte;
- l’action;
- le résultat attendu.

---

## Bonnes pratiques

✔ Utiliser des tests unitaires pour la logique pure.

✔ Utiliser des tests d’intégration pour les flux backend, base de données et sécurité.

✔ Utiliser des tests E2E pour les parcours utilisateur critiques.

✔ Ajouter un test avant de corriger une régression importante.

✔ Regrouper les tests par comportement plutôt que par hasard technique.

✔ Garder les données de test simples et explicites.

✔ Éviter les tests fragiles qui dépendent trop de détails visuels ou temporels.

---

## Anti-patterns

### Mauvais

Avoir beaucoup de tests qui vérifient seulement que les composants se rendent sans erreur.

### Pourquoi c’est problématique

Ce type de test donne une impression de sécurité sans protéger les comportements importants.

---

### Mauvais

Ne tester que le scénario heureux.

### Pourquoi c’est problématique

Les vrais problèmes surviennent souvent dans les refus, les états limites et les accès non autorisés.

---

### Mauvais

Écrire des tests impossibles à comprendre sans relire toute l’implémentation.

### Pourquoi c’est problématique

Un test doit documenter un comportement, pas devenir une deuxième source de confusion.

---

## Exemples

Bon nom de test :

```text
refuse la création d’une facture lorsqu’un utilisateur tente d’utiliser un client d’une autre organisation
```

Mauvais nom de test :

```text
test invoice route
```

---

## Cas réel MAD DevOps

MADSuite doit prioriser les tests sur :

- l’isolation multi-tenant;
- les routes de facturation;
- les paiements;
- les exports;
- les jobs asynchrones;
- les notifications;
- les conversions devis/factures;
- les modules d’assistance cognitive lorsqu’ils influencent l’interface ou les données.

---

## Exceptions

Un prototype exploratoire peut démarrer sans couverture complète.

Toutefois, avant une mise en production ou une livraison client, les comportements critiques doivent être couverts.
