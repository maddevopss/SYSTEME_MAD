# STD-401 — Environnements

## Règle d’or

Un environnement doit être clair, reproductible et impossible à confondre avec un autre.

---

## Objectif

Définir les règles de gestion des environnements pour les projets MAD DevOps.

Un environnement correspond à un contexte d’exécution précis : développement, test, préproduction, production ou démonstration.

---

## Pourquoi ce standard existe

Un projet logiciel change souvent de contexte avant d’être livré.

Sans règles claires, les environnements peuvent devenir confus :

- variables différentes sans documentation;
- base de données mal ciblée;
- configuration oubliée;
- données de test visibles;
- comportement différent entre local et production;
- livraison difficile à reproduire.

Ce standard réduit les erreurs de contexte.

---

## Niveau de maturité

🟢 Fondamental

Tout projet maintenu doit identifier clairement ses environnements.

---

## Champ d’application

Ce standard s’applique à :

- applications Web;
- API;
- SaaS;
- applications desktop;
- applications mobiles;
- bases de données;
- services externes;
- automatisations;
- démonstrations client.

---

## Règles obligatoires

### Nommer les environnements

Chaque environnement doit avoir un rôle clair.

Noms recommandés :

- `development`;
- `test`;
- `staging`;
- `production`;
- `demo`.

### Séparer les configurations

La configuration doit être séparée selon l’environnement.

Une configuration de développement ne doit pas être utilisée en production.

### Documenter les variables

Chaque projet doit documenter ses variables d’environnement importantes.

Le fichier `.env.example` ou l’équivalent doit permettre de comprendre les paramètres attendus sans exposer de secrets.

### Protéger la production

La production doit être traitée comme l’environnement le plus sensible.

Toute action en production doit être volontaire, comprise et réversible lorsque possible.

### Éviter les données réelles en local

Les données réelles ne doivent pas être copiées dans un environnement local sans nécessité, anonymisation ou mesure de protection adaptée.

---

## Bonnes pratiques

✔ Utiliser des noms explicites pour les environnements.

✔ Garder les URLs, clés publiques et services externes séparés.

✔ Identifier visuellement les environnements dans les interfaces internes.

✔ Documenter la procédure de démarrage local.

✔ Utiliser des données de test réalistes mais non sensibles.

✔ Vérifier l’environnement ciblé avant une migration ou un déploiement.

---

## Anti-patterns

### Mauvais

Utiliser la même base de données pour tester et produire.

### Pourquoi c’est problématique

Une erreur de test peut affecter des données importantes.

---

### Mauvais

Avoir des variables d’environnement non documentées.

### Pourquoi c’est problématique

Le projet devient difficile à installer, maintenir ou transférer.

---

### Mauvais

Ne pas savoir si une erreur vient du code ou de l’environnement.

### Pourquoi c’est problématique

Le diagnostic devient plus long et plus fragile.

---

## Exemple minimal

```text
Environnement : staging
Rôle : validation avant production
Base de données : dédiée staging
Services externes : clés de test
Données : fictives ou anonymisées
Déploiement : automatique après validation
```

---

## Cas réel MAD DevOps

MADSuite doit distinguer clairement :

- local development;
- test automatisé;
- staging;
- production;
- environnement de démonstration si nécessaire.

Chaque environnement doit utiliser une configuration séparée pour la base de données, les URLs frontend/backend, les paiements et les intégrations externes.

---

## Exceptions

Un prototype très court peut utiliser une configuration simplifiée.

Toutefois, avant une livraison client ou une mise en production, les environnements doivent être clarifiés.
