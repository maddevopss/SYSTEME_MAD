STD-202 — Autorisation

Règle d’or

Un utilisateur authentifié n’est pas automatiquement autorisé. Chaque action doit être explicitement permise.

⸻

Objectif

Définir les principes d’autorisation des applications développées par MAD DevOps.

L’autorisation consiste à déterminer les ressources et les actions auxquelles un utilisateur authentifié peut accéder.

Elle protège les fonctionnalités, les données et les opérations sensibles.

⸻

Pourquoi ce standard existe

Une authentification réussie confirme une identité.

Elle ne donne aucun droit.

Les permissions doivent être évaluées pour chaque ressource afin d’assurer le respect des rôles, des responsabilités et des limites de sécurité.

Une autorisation mal conçue peut exposer des données confidentielles ou permettre des actions non désirées.

⸻

Niveau de maturité

🟢 Fondamental

Ce standard s’applique à tous les projets développés par MAD DevOps.

⸻

Champ d’application

Ce standard s’applique à :

* toutes les applications Web;
* toutes les API;
* toutes les applications mobiles;
* toutes les applications desktop;
* tous les produits SaaS.

⸻

Règles obligatoires

Vérifier chaque accès

Chaque accès à une ressource protégée doit être validé.

Une vérification effectuée auparavant ne doit jamais être considérée comme suffisante.

⸻

Appliquer le principe du moindre privilège

Un utilisateur ne reçoit que les permissions nécessaires à son rôle.

Les privilèges supplémentaires doivent être explicitement accordés.

⸻

Les permissions sont contrôlées par le serveur

Le frontend peut masquer une fonctionnalité pour améliorer l’expérience utilisateur.

Toutefois, seule la logique serveur décide si une action est autorisée.

⸻

Les rôles ne suffisent pas toujours

Lorsque nécessaire, l’autorisation doit également tenir compte :

* de l’organisation;
* du propriétaire de la ressource;
* de l’état métier;
* du contexte d’exécution.

⸻

Refuser par défaut

En cas de doute, l’accès doit être refusé.

L’autorisation doit toujours être explicite.

⸻

Bonnes pratiques

✔ Centraliser les règles d’autorisation.

✔ Utiliser des rôles simples et compréhensibles.

✔ Journaliser les accès sensibles.

✔ Vérifier les permissions avant toute modification.

✔ Tester les scénarios d’accès refusé.

✔ Réviser régulièrement les permissions.

⸻

Anti-patterns

Mauvais

Autoriser une action uniquement parce que l’utilisateur est connecté.

⸻

Mauvais

Faire confiance au rôle transmis par le client.

⸻

Mauvais

Effectuer les contrôles uniquement dans l’interface utilisateur.

⸻

Mauvais

Dupliquer les règles d’autorisation dans plusieurs modules.

⸻

Bon

Chaque requête est validée côté serveur selon les permissions, le contexte et les règles métier applicables.

⸻

Exemples

Un utilisateur peut :

* consulter ses propres informations;
* modifier les ressources auxquelles il est autorisé;
* accéder uniquement aux données de son organisation.

Les permissions sont évaluées indépendamment de l’interface utilisée.

⸻

Cas réel MAD DevOps

MADSuite

MADSuite applique plusieurs niveaux d’autorisation :

* validation du JWT;
* vérification du rôle utilisateur;
* contrôle de l’organisation active;
* application des politiques RLS PostgreSQL;
* vérification des permissions métier.

Cette approche réduit considérablement le risque d’accès non autorisé.

⸻

Exceptions

Certaines ressources publiques peuvent être accessibles sans autorisation.

Toute exception doit être documentée et validée lors de la conception.

Citation

L’authentification répond à la question « Qui êtes-vous ? ». L’autorisation répond à la question « Que pouvez-vous faire ? ». Confondre les deux crée des vulnérabilités.
