# STD-403 — Déploiement

## Règle d’or

Un déploiement doit être préparé, observable et vérifiable.

---

## Objectif

Définir les règles de déploiement pour les projets MAD DevOps afin de livrer des changements de manière fiable, contrôlée et compréhensible.

---

## Pourquoi ce standard existe

Un déploiement n’est pas seulement une action technique.

C’est le moment où une modification quitte l’espace de développement pour toucher de vrais utilisateurs, de vraies données ou un vrai client.

Un déploiement mal préparé peut créer :

- interruption de service;
- confusion utilisateur;
- configuration incorrecte;
- données incohérentes;
- difficulté à diagnostiquer un problème;
- perte de confiance.

---

## Niveau de maturité

🟡 Intermédiaire

Tout projet livré à un client ou utilisé en production doit suivre une méthode de déploiement minimale.

---

## Champ d’application

Ce standard s’applique à :

- applications Web;
- API;
- SaaS;
- applications desktop;
- bases de données;
- services internes;
- automatisations;
- documentation publiée;
- changements de configuration.

---

## Règles obligatoires

### Connaître ce qui est déployé

Un déploiement doit être associé à un changement clair :

- fonctionnalité;
- correction;
- configuration;
- migration;
- documentation;
- version.

### Valider avant déploiement

Avant de déployer, appliquer les règles de validation avant livraison.

Les tests ou checklists pertinents doivent être exécutés selon le risque.

### Prévoir les migrations

Toute migration de base de données doit être traitée comme une étape sensible.

Elle doit être comprise, vérifiée et compatible avec le code livré.

### Vérifier après déploiement

Après déploiement, vérifier au minimum :

- démarrage de l’application;
- route ou page principale;
- logs récents;
- parcours critique;
- intégrations importantes.

### Documenter les déploiements importants

Un déploiement significatif doit laisser une trace :

- date;
- résumé du changement;
- environnement;
- validation effectuée;
- problème connu si applicable.

---

## Bonnes pratiques

✔ Déployer de petits changements plutôt que de très gros lots.

✔ Éviter les déploiements importants sans fenêtre de validation.

✔ Déployer d’abord dans un environnement de validation lorsque possible.

✔ Vérifier les variables d’environnement avant la livraison.

✔ Garder une procédure de retour ou correction rapide.

✔ Surveiller les logs immédiatement après la mise en ligne.

---

## Anti-patterns

### Mauvais

Déployer sans savoir exactement ce qui a changé.

### Pourquoi c’est problématique

Il devient difficile de diagnostiquer un problème après coup.

---

### Mauvais

Déployer une migration sans comprendre son impact.

### Pourquoi c’est problématique

Les données sont souvent plus difficiles à réparer que le code.

---

### Mauvais

Déployer et quitter sans vérification.

### Pourquoi c’est problématique

Le problème peut être découvert par le client au lieu d’être détecté par l’équipe.

```text
Problèmes connus :
```

---

## Cas réel MAD DevOps

Pour MADSuite, un déploiement doit vérifier au minimum :

- frontend accessible;
- backend accessible;
- connexion utilisateur;
- base de données disponible;
- configuration des URLs;
- création ou consultation d’un élément métier critique;
- absence d’erreur évidente dans les logs récents.

---

## Exceptions

Une démonstration temporaire peut avoir un processus plus léger.

Toutefois, si un client utilise réellement l’environnement, ce standard s’applique.

Déployer, ce n’est pas espérer que tout ira bien. C’est vérifier que ce qui devait arriver est bien arrivé.
