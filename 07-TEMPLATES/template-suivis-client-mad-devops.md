# Template — Suivis client MAD DevOps

## Objectif

Ce template regroupe les messages réutilisables à adapter pendant le parcours client MAD DevOps.

Il sert à garder les suivis clairs, professionnels et alignés avec l’approche MAD DevOps.

---

## Règle d’utilisation

Remplacer tous les champs entre crochets avant l’envoi.

Ne jamais envoyer un message qui promet un prix, un délai ou un livrable sans cadrage suffisant.

---

# 1. Après un premier échange

```text
Bonjour [Nom],

Merci pour l’échange.

Voici ce que je retiens :

- Problème principal : [problème]
- Résultat souhaité : [résultat]
- Utilisateurs concernés : [utilisateurs]
- Première version utile : [première version]
- Points à clarifier : [questions]

À ce stade, la prochaine étape recommandée est : [découverte / cadrage / Phase 0 / proposition].

Merci,
MAD DevOps
```

---

# 2. Quand le besoin est flou

```text
Bonjour [Nom],

Le besoin semble important, mais il reste encore des éléments à clarifier avant de proposer une solution juste.

Je recommande de commencer par un court cadrage afin de préciser :

- le problème réel;
- la première version utile;
- le périmètre;
- les risques;
- la prochaine décision.

Cela évite de partir trop large ou de proposer une solution qui ne règle pas le bon problème.

Merci,
MAD DevOps
```

---

# 3. Proposition d’une Phase 0

```text
Bonjour [Nom],

Le projet semble intéressant, mais il y a trop de variables pour s’engager directement sur une réalisation complète.

Je recommande une Phase 0 de cadrage / diagnostic.

L’objectif serait de clarifier :

- le besoin réel;
- les utilisateurs concernés;
- les options possibles;
- les risques;
- la première version utile;
- la feuille de route recommandée.

À la fin de cette étape, nous pourrons décider clairement si le projet doit continuer, être réduit, être reporté ou être découpé en phases.

Merci,
MAD DevOps
```

---

# 4. Après un cadrage

```text
Bonjour [Nom],

Voici la synthèse du cadrage.

Le besoin principal est : [besoin].

La première version utile devrait permettre de : [résultat].

Le périmètre recommandé est :

- [élément 1]
- [élément 2]
- [élément 3]

Les éléments suivants seraient mieux gardés pour une phase future :

- [hors périmètre 1]
- [hors périmètre 2]

Les principaux risques ou points à clarifier sont :

- [risque 1]
- [risque 2]

La prochaine étape recommandée est : [proposition / Phase 0 / informations supplémentaires].

Merci,
MAD DevOps
```

---

# 5. Envoi d’une proposition

```text
Bonjour [Nom],

Vous trouverez ci-joint la proposition pour [nom du projet].

Elle résume :

- le contexte;
- le besoin identifié;
- la solution proposée;
- les livrables;
- le hors périmètre;
- les responsabilités;
- l’échéancier estimé;
- la prochaine action.

L’objectif est que tout soit clair avant de démarrer.

Merci,
MAD DevOps
```

---

# 6. Avant livraison

```text
Bonjour [Nom],

Le livrable est prêt pour validation.

Avant de considérer la livraison comme terminée, voici les éléments à vérifier :

- [élément 1]
- [élément 2]
- [élément 3]

Les limites connues sont :

- [limite 1]
- [limite 2]

Merci de me confirmer si le tout correspond au périmètre prévu ou si un point doit être corrigé.

Merci,
MAD DevOps
```

---

# 7. Après livraison

```text
Bonjour [Nom],

La livraison de [nom du projet] est complétée.

Voici ce qui a été livré :

- [livrable 1]
- [livrable 2]
- [livrable 3]

Informations utiles :

- Accès : [lien ou indication]
- Documentation : [lien ou indication]
- Limites connues : [si applicable]

Prochaine étape recommandée : [suivi / amélioration / maintenance / nouvelle phase].

Merci pour la confiance,
MAD DevOps
```

---

# 8. Demande d’information manquante

```text
Bonjour [Nom],

Pour avancer correctement, il me manque quelques éléments :

- [élément 1]
- [élément 2]
- [élément 3]

Dès que ces informations seront disponibles, je pourrai confirmer la prochaine étape.

Merci,
MAD DevOps
```

---

# 9. Refus ou report poli

```text
Bonjour [Nom],

Après analyse, je ne crois pas que ce soit responsable de démarrer le projet dans les conditions actuelles.

Le besoin mérite d’être clarifié davantage avant de s’engager sur une solution.

Je préfère le signaler maintenant plutôt que de proposer quelque chose qui risque de ne pas répondre au bon problème.

La prochaine étape recommandée serait : [cadrage / Phase 0 / report / autre].

Merci,
MAD DevOps
```
