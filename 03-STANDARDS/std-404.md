# STD-404 — Observabilité

## Règle d’or

Un système qu’on ne peut pas observer devient difficile à comprendre, maintenir et améliorer.

---

## Objectif

Définir les principes d’observabilité pour les projets MAD DevOps afin de comprendre l’état réel d’une application, diagnostiquer les problèmes et suivre les comportements importants.

L’observabilité regroupe les informations qui permettent de répondre à une question simple : que se passe-t-il dans le système ?

---

## Pourquoi ce standard existe

Un système peut sembler fonctionner tout en cachant :

- erreurs silencieuses;
- lenteurs;
- tâches planifiées qui échouent;
- intégrations instables;
- parcours utilisateur bloqués;
- comportements incohérents;
- problèmes de configuration.

Sans observabilité, les problèmes sont découverts trop tard ou par les utilisateurs.

---

## Niveau de maturité

🟡 Intermédiaire

Tout projet en production doit posséder une observabilité minimale.

---

## Champ d’application

Ce standard s’applique à :

- backend;
- frontend;
- SaaS;
- applications desktop;
- jobs asynchrones;
- intégrations externes;
- paiements;
- exports;
- modules IA;
- tâches planifiées.

---

## Règles obligatoires

### Journaliser les événements importants

Le système doit conserver une trace utile des événements importants.

Exemples :

- démarrage d’un service;
- erreur applicative;
- tâche planifiée exécutée;
- intégration externe appelée;
- paiement ou événement financier;
- changement critique de configuration;
- action sensible d’administration.

### Éviter les logs inutiles

Un log doit aider à comprendre le système.

Des logs trop nombreux, trop vagues ou trop bruyants rendent le diagnostic plus difficile.

### Protéger les données sensibles

Les logs ne doivent pas contenir inutilement :

- mots de passe;
- clés privées;
- jetons;
- secrets;
- données personnelles complètes;
- informations financières sensibles.

### Suivre les erreurs

Les erreurs importantes doivent pouvoir être retrouvées avec un minimum de contexte.

Le contexte utile peut inclure :

- module;
- action;
- environnement;
- type d’erreur;
- identifiant technique non sensible;
- date et heure.

### Surveiller les tâches automatisées

Les jobs, workers et tâches planifiées doivent laisser une trace de leur exécution.

Il doit être possible de savoir si une tâche :

- a démarré;
- a réussi;
- a échoué;
- a été partiellement complétée;
- n’a pas été exécutée depuis trop longtemps.

---

## Bonnes pratiques

✔ Utiliser des niveaux de logs cohérents.

✔ Ajouter des identifiants de corrélation lorsque pertinent.

✔ Créer des points de santé pour les services importants.

✔ Suivre les erreurs récurrentes.

✔ Surveiller les temps de réponse des parcours critiques.

✔ Documenter les événements importants à surveiller.

✔ Réduire le bruit avant d’ajouter plus de logs.

---

## Anti-patterns

### Mauvais

Afficher seulement “Erreur inconnue”.

### Pourquoi c’est problématique

Le message ne permet pas de comprendre où chercher.

---

### Mauvais

Journaliser trop de détails sensibles.

### Pourquoi c’est problématique

Les logs deviennent une source de risque.

---

### Mauvais

Découvrir qu’un job ne fonctionne plus seulement plusieurs jours plus tard.

### Pourquoi c’est problématique

Une tâche silencieuse peut créer des effets cumulatifs importants.

---

## Exemple minimal

```text
Event: invoice.created
Environment: production
Organisation: org_123
User: user_456
Result: success
Timestamp: 2026-06-30T12:00:00
```

Les identifiants doivent rester techniques et limiter l’exposition de données sensibles.

---

## Cas réel MAD DevOps

Pour MADSuite, l’observabilité doit couvrir progressivement :

- authentification;
- facturation;
- paiements;
- jobs de relance;
- génération PDF;
- WebSockets;
- exports;
- métriques système;
- tâches planifiées;
- erreurs frontend importantes.

---

## Exceptions

Un prototype local peut avoir une observabilité minimale.

Toutefois, dès qu’un utilisateur réel dépend du système, les événements critiques doivent être observables.
