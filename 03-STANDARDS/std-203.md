STD-203 — Gestion des secrets

Règle d’or

Un secret qui apparaît dans le code n’est plus un secret.

---

Objectif

Définir les principes de gestion des secrets afin de protéger les informations sensibles utilisées par les applications développées par MAD DevOps.

Les secrets doivent être protégés tout au long de leur cycle de vie : création, stockage, utilisation, rotation et suppression.

---

Pourquoi ce standard existe

Les secrets permettent à une application de communiquer avec d’autres systèmes et d’accéder à des ressources protégées.

Une mauvaise gestion peut entraîner :

* une fuite de données;
* une compromission de comptes;
* un accès non autorisé;
* des pertes financières;
* une atteinte à la réputation.

---

Niveau de maturité

🟢 Fondamental

Ce standard s’applique à tous les projets développés par MAD DevOps.

---

Champ d’application

Ce standard s’applique à :

* toutes les applications;
* toutes les API;
* toutes les applications Web;
* toutes les applications mobiles;
* toutes les applications desktop;
* tous les services d’infrastructure.

---

Règles obligatoires

Ne jamais versionner un secret

Les secrets ne doivent jamais être enregistrés dans Git ou tout autre système de contrôle de version.

Les fichiers contenant des secrets doivent être exclus du dépôt.

---

Utiliser des variables d’environnement ou un gestionnaire de secrets

Les informations sensibles doivent être fournies au moment du déploiement.

Le code source ne doit jamais contenir :

* mots de passe;
* clés API;
* jetons;
* certificats privés;
* chaînes de connexion complètes.

---

Limiter l’accès

Seules les personnes et les services qui en ont réellement besoin doivent avoir accès aux secrets.

Le principe du moindre privilège s’applique également aux secrets.

---

Prévoir la rotation

Les secrets doivent pouvoir être remplacés sans modifier le code.

Une procédure de rotation doit être prévue pour les systèmes critiques.

---

Révoquer immédiatement un secret compromis

Tout secret soupçonné d’être compromis doit être remplacé sans délai.

La révocation doit faire partie du plan d’intervention.

---

Bonnes pratiques

✔ Utiliser un gestionnaire de secrets lorsque possible.

✔ Fournir un fichier .env.example sans valeurs sensibles.

✔ Journaliser les accès aux secrets lorsque pertinent.

✔ Utiliser des clés différentes selon les environnements.

✔ Vérifier régulièrement les dépôts pour détecter les fuites accidentelles.

✔ Documenter les procédures de rotation.

---

Anti-patterns

Mauvais

const STRIPE_SECRET = "sk_live_xxxxxxxxx";

---

Mauvais

Partager un fichier .env par courriel ou messagerie.

---

Mauvais

Réutiliser le même secret en développement, test et production.

---

Bon

Les secrets sont fournis par l’environnement d’exécution et ne figurent jamais dans le code source.

---

Exemples

Les éléments suivants sont considérés comme des secrets :

* clés OpenAI;
* clés Stripe;
* secrets JWT;
* mots de passe de base de données;
* certificats privés;
* clés SSH;
* jetons OAuth.

---

Cas réel MAD DevOps

MADSuite

MADSuite utilise des variables d’environnement pour gérer les secrets liés à PostgreSQL, JWT, Stripe, OpenAI et aux différents services externes.

Les fichiers .env sont exclus du dépôt Git et un fichier .env.example documente les paramètres attendus sans exposer d’informations sensibles.

Les environnements de développement, de test et de production utilisent des secrets distincts.

---

Exceptions

Aucune exception n’est permise concernant le stockage de secrets dans le code source.

Les seules constantes autorisées sont celles qui ne permettent pas d’accéder à une ressource protégée.
