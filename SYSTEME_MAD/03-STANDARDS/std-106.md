# STD-106 — Responsive mobile et interfaces adaptatives

## Règle d’or

Aucun composant ne doit dépendre d’une largeur desktop fixe.

Sur mobile :

- toute grille doit pouvoir tomber en 1 colonne ;
- tout tableau doit être dans un wrapper scrollable interne ou converti en cartes ;
- le scroll horizontal global est interdit ;
- les boutons, inputs, modales, drawers et cartes doivent rester dans le viewport ;
- les composants flottants doivent respecter la safe-area iPhone et ne jamais cacher les CTA principaux.

---

## Objectif

Garantir que les interfaces MAD DevOps et MADSuite restent utilisables, lisibles et stables sur mobile, tablette et desktop.

Le responsive ne doit pas être traité comme une correction cosmétique. Il fait partie de la qualité produit, de l’accessibilité et de l’expérience client.

---

## Champ d’application

Ce standard s’applique à :

- MADSuite frontend web ;
- interfaces mobiles web ;
- interfaces desktop avec fenêtres redimensionnables ;
- composants React partagés ;
- dashboards ;
- formulaires ;
- tableaux ;
- drawers, modales et composants flottants.

---

## Règles obligatoires

### 1. Interdire le scroll horizontal global

Aucune page ne doit produire un scroll horizontal global sur les breakpoints mobiles.

Le scroll horizontal n’est permis que dans un conteneur interne contrôlé, par exemple un wrapper de tableau.

### 2. Éviter les largeurs desktop fixes

Les composants ne doivent pas imposer de largeur fixe qui dépasse le viewport mobile.

À éviter :

```css
width: 900px;
min-width: 900px;
```

À privilégier :

```css
width: 100%;
max-width: 100%;
min-width: 0;
```

### 3. Adapter les grilles

Toute grille desktop doit avoir une stratégie mobile.

Exemple :

```css
@media (max-width: 768px) {
  .grid {
    grid-template-columns: 1fr;
  }
}
```

### 4. Encadrer les tableaux

Un tableau doit respecter une des deux approches :

- wrapper scrollable interne ;
- transformation en cartes mobiles.

Exemple wrapper :

```css
.table-responsive {
  width: 100%;
  overflow-x: auto;
  -webkit-overflow-scrolling: touch;
}
```

### 5. Protéger les formulaires mobiles

Sur mobile :

- les inputs doivent rester à `width: 100%` ;
- les labels doivent rester visibles ;
- les boutons principaux doivent rester accessibles ;
- les modales ne doivent pas dépasser le viewport.

### 6. Drawer mobile

Un drawer mobile doit :

- être fermé par défaut ;
- s’ouvrir au-dessus du contenu ;
- ne jamais pousser le contenu principal ;
- avoir un overlay si nécessaire ;
- se fermer au clic extérieur ou après sélection d’un item lorsque pertinent.

### 7. Safe-area iPhone

Les éléments flottants et bas de page doivent respecter :

```css
padding-bottom: env(safe-area-inset-bottom);
```

ou une variante contrôlée lorsque nécessaire.

### 8. Protéger les corrections critiques par tests

Toute correction responsive critique doit être protégée par au moins un test anti-régression Playwright vérifiant :

- l’absence de scroll horizontal global ;
- la visibilité du contenu principal ;
- la stabilité desktop ;
- au minimum les breakpoints 390px et 1440px.

La checklist opérationnelle associée est :

```text

```

## Breakpoints minimaux à valider

Une page critique doit être vérifiée au minimum sur :

- 375px ;
- 390px ;
- 430px ;
- 768px ;
- 1440px.

---

## Pages critiques MADSuite

Les pages suivantes doivent être surveillées en priorité :

- Dashboard ;
- Timesheet / Feuilles de temps ;
- Clients ;
- Projets ;
- Soumissions / Estimates ;
- Facturation / Invoices ;
- Reports ;
- Settings.

---

## Critères d’acceptation

Une page mobile est conforme seulement si :

1. aucun scroll horizontal global n’apparaît ;
2. les informations métier restent accessibles ;
3. les actions principales restent visibles et cliquables ;
4. les tableaux sont contenus dans un scroll interne ou transformés en cartes ;
5. le drawer mobile ne pousse jamais le contenu ;
6. les composants flottants ne cachent pas les CTA principaux ;
7. le desktop reste visuellement stable ;
8. une correction responsive critique est protégée par un test anti-régression.

---

## Anti-patterns

À éviter :

- masquer un problème uniquement avec `overflow-x: hidden` ;
- introduire une largeur fixe desktop dans un composant partagé ;
- corriger le mobile en cassant le desktop ;
- modifier la logique métier pour une correction responsive ;
- ajouter une librairie UI seulement pour contourner un problème CSS local ;
- livrer une correction responsive critique sans test anti-régression minimal.
