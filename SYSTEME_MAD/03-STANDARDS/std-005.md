STD-005 — Documentation du code

Règle d’or

Nous documentons les décisions, pas les évidences.

---

Objectif

Définir les règles de documentation du code afin d’améliorer la compréhension, la maintenance et la transmission des connaissances.

Une bonne documentation permet de comprendre rapidement le fonctionnement d’un projet sans devoir analyser chaque ligne de code.

---

Pourquoi ce standard existe

Le code évolue constamment.

Les personnes qui le lisent changent.

La mémoire humaine est limitée.

La documentation permet de préserver les connaissances importantes et d’expliquer les décisions qui ne sont pas visibles dans le code.

---

Niveau de maturité

🟢 Fondamental

Ce standard s’applique à tous les projets développés par MAD DevOps.

---

Champ d’application

Ce standard s’applique à :

* toutes les applications;
* toutes les bibliothèques;
* toutes les API;
* tous les modules réutilisables;
* tous les projets internes;
* tous les projets clients.

---

Règles obligatoires

Le code doit être compréhensible sans commentaires

Les commentaires ne doivent jamais compenser un code difficile à lire.

Si un commentaire explique ce que fait chaque ligne, le code devrait probablement être simplifié.

---

Documenter les décisions importantes

Les commentaires servent principalement à expliquer :

* pourquoi une solution a été choisie;
* une contrainte particulière;
* une limitation connue;
* un comportement inhabituel.

---

README obligatoire

Chaque projet doit posséder un README décrivant :

* l’objectif;
* l’installation;
* le démarrage;
* l’architecture générale;
* les principales dépendances.

---

Documentation publique

Les API, bibliothèques ou modules réutilisables doivent être documentés.

---

Documentation synchronisée

La documentation doit évoluer en même temps que le code.

Une documentation obsolète est souvent plus nuisible qu’une absence de documentation.

---

Bonnes pratiques

✔ Écrire pour la personne qui découvrira le projet.

✔ Utiliser un langage simple.

✔ Maintenir les README à jour.

✔ Ajouter des exemples.

✔ Utiliser JSDoc, TypeDoc ou l’équivalent lorsque pertinent.

✔ Documenter les décisions architecturales dans des ADR.

---

Anti-patterns

Mauvais

// Incrémente i
i++;

Le commentaire n’apporte aucune valeur.

---

Mauvais

// TODO : Corriger plus tard

Sans contexte, sans responsable et sans échéance.

---

Bon

// Cette validation est conservée afin de
// demeurer compatible avec les anciens clients.
// Voir ADR-012.

Le commentaire explique la raison de la décision.

---

Exemples

Une bonne documentation répond aux questions suivantes :

* Pourquoi ce module existe-t-il ?
* Quel problème résout-il ?
* Comment doit-il être utilisé ?
* Quelles sont ses limites ?
* Existe-t-il des décisions importantes associées ?

---

Cas réel MAD DevOps

MADSuite

Le développement de MADSuite a démontré l’importance de documenter les décisions techniques.

La création des ADR, des Standards et du Handbook permet aujourd’hui de comprendre rapidement les choix architecturaux, les conventions de développement et les principes qui guident le projet.

Cette documentation facilite autant le développement que la maintenance et l’intégration de nouvelles fonctionnalités.

---

Exceptions

Les prototypes, les preuves de concept (POC) ou les expérimentations peuvent être moins documentés.

Toutefois, si un prototype devient un produit officiel, sa documentation doit être complétée avant sa mise en production.
