# CHK-036 — Validation rapport mensuel Early Access MADSuite

## Objectif

Cette checklist valide qu’un rapport mensuel Early Access MADSuite est utile, clair, orienté décision et aligné avec le Revenue Core.

Elle doit être utilisée avant de finaliser ou partager un rapport mensuel Early Access.

## 1. Identification du rapport

- [ ] Le mois analysé est indiqué.
- [ ] La période couverte est claire.
- [ ] Les sources utilisées sont listées.
- [ ] La version produit concernée est indiquée.
- [ ] Le responsable du rapport est identifié.

Notes :

```text
Mois :
Période :
Responsable :
Version produit :
Sources :
```

---

## 2. Résumé exécutif

- [ ] Le rapport commence par une synthèse courte.
- [ ] Les 3 principaux apprentissages sont visibles.
- [ ] La décision principale recommandée est claire.
- [ ] Le rapport ne recopie pas tous les commentaires reçus.
- [ ] Le rapport aide à décider quoi faire ensuite.

---

## 3. Métriques clés

- [ ] Les demandes Early Access sont indiquées.
- [ ] Les invitations envoyées sont indiquées.
- [ ] Les activations sont indiquées.
- [ ] Les premières actions produit sont indiquées lorsque disponibles.
- [ ] Les premières factures sont indiquées lorsque disponibles.
- [ ] Les feedbacks reçus sont indiqués.
- [ ] Les feedbacks analysés sont indiqués.
- [ ] Les métriques sont accompagnées d’un court commentaire utile.

---

## 4. Activation et première valeur

- [ ] Le rapport indique si les utilisateurs comprennent comment commencer.
- [ ] Le rapport évalue le chemin vers la première facture.
- [ ] Le rapport identifie l’étape qui ralentit le plus la première valeur.
- [ ] Le rapport distingue observation, hypothèse et décision.
- [ ] Une action recommandée est proposée.

---

## 5. Signaux Revenue Core

- [ ] Les signaux clients sont vérifiés.
- [ ] Les signaux projets sont vérifiés.
- [ ] Les signaux temps sont vérifiés.
- [ ] Les signaux factures sont vérifiés.
- [ ] Les signaux PDF sont vérifiés.
- [ ] Les signaux estimés sont vérifiés si applicables.
- [ ] Les signaux paiements sont vérifiés si applicables.
- [ ] Les signaux dashboard revenus sont vérifiés.
- [ ] Les priorités restent liées au Revenue Core.

---

## 6. Feedback et apprentissages

- [ ] Les retours sont regroupés en tendances.
- [ ] Les signaux isolés ne sont pas surpondérés.
- [ ] Les top apprentissages sont reliés à une action possible.
- [ ] Les frictions principales sont identifiées.
- [ ] Les demandes hors priorité sont notées sans prendre toute la place.

---

## 7. Backlog post-feedback

- [ ] Les items P0/P1 sont identifiés.
- [ ] Chaque item est relié à un problème utilisateur.
- [ ] Chaque item est relié à un parcours Revenue Core ou à une justification claire.
- [ ] Les items P2/P3 sont séparés des priorités immédiates.
- [ ] Les items reportés ont une raison courte.

---

## 8. Décisions produit

- [ ] Les décisions existantes à confirmer sont listées.
- [ ] Les nouvelles décisions proposées sont listées.
- [ ] Les décisions à reporter sont listées.
- [ ] Le registre des décisions produit est identifié comme document cible si nécessaire.
- [ ] Aucune décision importante n’est cachée dans le texte sans être explicitée.

---

## 9. Risques et limites

- [ ] Le risque de complexifier le MVP est vérifié.
- [ ] Le risque de sortir du Revenue Core est vérifié.
- [ ] Le risque de message public trop fort est vérifié.
- [ ] Le risque de collecte inutile est vérifié.
- [ ] Le risque de confusion sur prix ou accès est vérifié.
- [ ] Les limites du mois sont indiquées clairement.

---

## 10. Priorités du mois suivant

- [ ] Les priorités du mois suivant sont listées.
- [ ] Chaque priorité a une justification courte.
- [ ] Chaque priorité a un document ou parcours lié.
- [ ] Les priorités sont réalistes pour le mois suivant.
- [ ] Le rapport ne crée pas plus de travail que ce qu’il aide à clarifier.

---

## 11. Vérification MADPROOF

- [ ] Le rapport ne contient pas de claim médical.
- [ ] Le rapport ne promet pas d’effet non validé.
- [ ] Le rapport ne présente pas les feedbacks comme preuve clinique.
- [ ] Le rapport reste centré sur l’usage produit et le contexte opérationnel.
- [ ] Si un claim sensible est présent, `CHK-032` est appliquée.

---

## 12. Verdict

- [ ] Prêt à partager.
- [ ] Prêt avec corrections mineures.
- [ ] À reprendre avant partage.
- [ ] Non partageable en l’état.

```text

```

## Phrase de contrôle

> Est-ce que ce rapport aide à choisir les prochaines priorités sans noyer l’équipe dans les détails?
