STD-001 — Convention de codage

Règle d’or

Le meilleur code n’est pas celui qui impressionne. C’est celui qui est compris rapidement, facilement et durablement.

⸻

Objectif

Définir les conventions de codage utilisées dans tous les projets développés par MAD DevOps afin d’assurer la cohérence, la lisibilité, la maintenabilité et la qualité du code.

⸻

Pourquoi ce standard existe

Chaque ligne de code est susceptible d’être relue, modifiée ou corrigée plusieurs années après sa création.

Une convention commune réduit les erreurs, accélère le développement et facilite la collaboration.

Nous écrivons du code pour les humains avant de l’écrire pour les ordinateurs.

⸻

Champ d’application

Ce standard s’applique à :

* tous les projets logiciels;
* toutes les applications Web;
* toutes les applications mobiles;
* toutes les applications desktop;
* tous les scripts d’automatisation;
* toutes les contributions réalisées pour MAD DevOps.

⸻

Règles obligatoires

Lisibilité

Le code doit être simple à lire.

Les noms doivent être explicites.

Une personne découvrant le projet doit comprendre rapidement son fonctionnement.

⸻

Responsabilité unique

Chaque fonction, classe ou module doit avoir une seule responsabilité clairement définie.

⸻

Fonctions

Les fonctions doivent :

* avoir un objectif précis;
* être courtes lorsque possible;
* éviter les effets de bord inutiles;
* retourner un résultat prévisible.

⸻

Variables

Les variables doivent utiliser des noms significatifs.

Éviter :

* a
* tmp
* data
* value

lorsqu’un nom plus précis est possible.

⸻

Constantes

Les valeurs fixes doivent être déclarées comme constantes.

Éviter les “magic numbers”.

⸻

Duplication

Éviter la duplication de code.

Si une logique est utilisée plusieurs fois, elle devrait être centralisée.

⸻

Commentaires

Les commentaires doivent expliquer :

* pourquoi une décision a été prise;
* une contrainte particulière;
* un comportement non évident.

Ils ne doivent jamais décrire ce que le code indique déjà.

⸻

Refactoring

Lorsque cela est raisonnable, laisser le code légèrement meilleur que lors de son arrivée.

⸻

Bonnes pratiques

✔ Utiliser des noms explicites.

✔ Respecter les conventions du langage utilisé.

✔ Préférer la simplicité.

✔ Isoler les responsabilités.

✔ Favoriser les fonctions réutilisables.

✔ Supprimer le code mort.

✔ Limiter les dépendances inutiles.

✔ Garder les fichiers organisés.

⸻

Anti-patterns

Mauvais

let a = 10;
let b = 20;
let c = a * b;

Pourquoi ?

Le code fonctionne.

Mais il ne communique aucune intention.

⸻

Bon

const heuresTravaillees = 10;
const tauxHoraire = 20;
const montantFacture = heuresTravaillees * tauxHoraire;

Le code explique immédiatement son objectif.

⸻

Exemples

✔ Une fonction effectue une seule tâche.

✔ Une classe possède une responsabilité unique.

✔ Les constantes remplacent les valeurs magiques.

✔ Les modules sont indépendants lorsque possible.

⸻

Exceptions

Certaines optimisations ou contraintes techniques peuvent justifier une exception.

Toute exception importante doit être documentée et comprise par l’équipe.
