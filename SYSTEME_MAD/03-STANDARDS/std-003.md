STD-003 — Gestion des erreurs

Règle d’or

Une erreur bien gérée inspire davantage confiance qu’une erreur cachée.

---

Objectif

Définir les principes de gestion des erreurs afin d’assurer la stabilité des applications, de faciliter le diagnostic des problèmes et d’offrir une expérience utilisateur claire et rassurante.

Une erreur ne doit jamais être ignorée.

Elle doit être comprise, traitée et, lorsque nécessaire, communiquée de manière appropriée.

---

Pourquoi ce standard existe

Les erreurs font partie du développement logiciel.

Ce qui distingue une solution robuste d’une solution fragile n’est pas l’absence d’erreurs, mais la manière dont elles sont gérées.

Une bonne gestion des erreurs permet :

* d’améliorer la stabilité;
* de simplifier le support;
* de faciliter le débogage;
* de renforcer la confiance des utilisateurs.

---

Niveau de maturité

🟢 Fondamental

Ce standard s’applique à tous les projets MAD DevOps.

---

Champ d’application

Ce standard s’applique à :

* toutes les API;
* toutes les applications Web;
* toutes les applications mobiles;
* toutes les applications desktop;
* tous les services d’arrière-plan;
* tous les scripts d’automatisation.

---

Règles obligatoires

Les erreurs ne doivent jamais être ignorées

Toute erreur doit être :

* traitée;
* journalisée lorsque pertinent;
* communiquée correctement.

---

Les messages destinés aux utilisateurs doivent être compréhensibles

Un utilisateur ne doit jamais voir :

* une trace de pile (stack trace);
* une exception brute;
* un message technique incompréhensible.

Les messages doivent expliquer le problème sans exposer d’informations sensibles.

---

Les messages destinés aux développeurs doivent être précis

Les journaux doivent permettre de comprendre rapidement :

* où l’erreur est survenue;
* pourquoi elle est survenue;
* dans quel contexte.

---

Ne jamais masquer une erreur importante

Capturer une exception sans traitement est interdit.

Une erreur silencieuse est souvent plus dangereuse qu’une erreur visible.

---

Toujours protéger les informations sensibles

Les erreurs ne doivent jamais révéler :

* mots de passe;
* jetons d’accès;
* clés API;
* informations personnelles;
* requêtes SQL complètes.

---

Bonnes pratiques

✔ Utiliser des exceptions adaptées.

✔ Retourner des codes HTTP cohérents.

✔ Journaliser les erreurs importantes.

✔ Ajouter un identifiant de corrélation lorsque possible.

✔ Séparer les erreurs métier des erreurs système.

✔ Fournir une solution lorsque cela est possible.

---

Anti-patterns

Mauvais

try {
    traiterFacture();
} catch (error) {
}

L’erreur disparaît complètement.

Impossible de comprendre le problème.

---

Mauvais

return res.status(500).send(error.stack);

Expose des informations internes.

---

Bon

logger.error("Erreur lors de la création de la facture", {
    invoiceId,
    organisationId,
    error: error.message,
});
return res.status(500).json({
    message: "Une erreur est survenue. Veuillez réessayer plus tard."
});

L’utilisateur reçoit un message clair.

Le développeur dispose des informations nécessaires dans les journaux.

---

Exemples

Erreur utilisateur

* champ obligatoire manquant;
* mot de passe incorrect;
* fichier invalide.

→ Message simple et explicite.

---

Erreur métier

* facture déjà payée;
* projet archivé;
* licence expirée.

→ Expliquer clairement la raison.

---

Erreur système

* base de données inaccessible;
* serveur indisponible;
* service externe hors ligne.

→ Journaliser l’erreur et informer l’utilisateur sans révéler de détails techniques.

---

Cas réel MAD DevOps

MADSuite

Lors du développement de MADSuite, toutes les routes API retournent des messages adaptés au contexte.

Les détails techniques sont consignés dans les journaux applicatifs.

Les utilisateurs reçoivent uniquement les informations nécessaires pour comprendre la situation.

Cette approche réduit les risques de fuite d’information tout en facilitant le support technique.

---

Exceptions

Dans certains environnements de développement, les erreurs détaillées peuvent être affichées afin de faciliter le débogage.

Cette pratique est strictement interdite en production.
