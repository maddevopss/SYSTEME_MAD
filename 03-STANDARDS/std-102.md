STD-102 — API REST

Règle d’or

Une API doit être intuitive, cohérente et prévisible.

---

Objectif

Définir les principes de conception des API REST afin d’assurer une expérience uniforme, une maintenance simplifiée et une intégration efficace entre les différents systèmes.

Une API constitue un contrat entre les applications. Ce contrat doit demeurer stable, clair et documenté.

---

Pourquoi ce standard existe

Une API incohérente devient rapidement difficile à utiliser, à maintenir et à faire évoluer.

En appliquant des conventions communes, nous facilitons :

* le développement;
* les intégrations;
* les tests;
* la maintenance;
* l’évolution des systèmes.

---

Niveau de maturité

🟡 Intermédiaire

Toute personne développant une API pour MAD DevOps doit respecter ce standard.

---

Champ d’application

Ce standard s’applique à :

* toutes les API REST;
* tous les services backend;
* les applications Web;
* les applications mobiles;
* les applications desktop;
* les intégrations entre systèmes.

---

Règles obligatoires

Utiliser les verbes HTTP appropriés

* GET → Lire
* POST → Créer
* PUT → Remplacer
* PATCH → Modifier partiellement
* DELETE → Supprimer

---

Utiliser des noms cohérents

Les routes doivent représenter des ressources.

Exemples :

/api/clients
/api/projects
/api/invoices

Éviter les verbes dans les URL.

---

Retourner des codes HTTP appropriés

Utiliser les codes standards :

* 200 OK
* 201 Created
* 204 No Content
* 400 Bad Request
* 401 Unauthorized
* 403 Forbidden
* 404 Not Found
* 409 Conflict
* 422 Unprocessable Entity
* 500 Internal Server Error

---

Uniformiser les réponses

Toutes les réponses doivent suivre une structure cohérente.

Exemple :

{
  "success": true,
  "data": {}
}

En cas d’erreur :

{
  "success": false,
  "message": "Description de l'erreur."
}

---

Versionner les API lorsque nécessaire

Les changements incompatibles doivent être versionnés afin de préserver la compatibilité des intégrations existantes.

---

Bonnes pratiques

✔ Utiliser des noms au pluriel.

✔ Rester cohérent dans toute l’API.

✔ Limiter le nombre de niveaux dans les routes.

✔ Valider toutes les entrées.

✔ Documenter chaque endpoint.

✔ Utiliser une authentification appropriée.

✔ Prévoir la pagination lorsque nécessaire.

---

Anti-patterns

Mauvais

/getClients

Le verbe HTTP indique déjà l’action.

---

Mauvais

/api/client/create

Le POST suffit à exprimer la création.

---

Bon

GET    /api/clients
POST   /api/clients
GET    /api/clients/{id}
PATCH  /api/clients/{id}
DELETE /api/clients/{id}

Une structure uniforme facilite la compréhension.

---

Exemples

Une API bien conçue permet à un développeur de deviner le fonctionnement d’un endpoint sans consulter la documentation.

La cohérence est plus importante que la créativité.

---

Cas réel MAD DevOps

MADSuite

L’API de MADSuite suit une structure REST uniforme :

* ressources identifiées par des noms au pluriel;
* utilisation cohérente des verbes HTTP;
* authentification JWT;
* réponses JSON homogènes;
* séparation claire entre les routes, les contrôleurs et les services.

Cette approche facilite l’évolution du backend ainsi que l’intégration du frontend React et de l’application Electron.

---

Exceptions

Certaines intégrations avec des services tiers peuvent imposer des conventions différentes.

Dans ce cas, les écarts doivent être documentés et isolés autant que possible.
