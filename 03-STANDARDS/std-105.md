STD-105 — Gestion de la configuration

Règle d’or

Une application doit pouvoir changer d’environnement sans modifier son code.

---

Objectif

Définir les principes de gestion de la configuration afin de garantir la sécurité, la portabilité et la reproductibilité des applications développées par MAD DevOps.

La configuration doit être indépendante du code source.

---

Pourquoi ce standard existe

Les applications évoluent dans plusieurs environnements :

* développement;
* test;
* préproduction;
* production.

Une gestion rigoureuse de la configuration réduit les erreurs de déploiement, protège les informations sensibles et facilite l’automatisation.

---

Niveau de maturité

🟡 Intermédiaire

Toute personne développant ou déployant une application doit respecter ce standard.

---

Champ d’application

Ce standard s’applique à :

* toutes les applications;
* toutes les API;
* toutes les applications Web;
* toutes les applications mobiles;
* toutes les applications desktop;
* tous les services d’infrastructure.

---

Règles obligatoires

Séparer la configuration du code

Les paramètres de configuration ne doivent jamais être codés directement dans l’application.

Ils doivent être externalisés.

---

Utiliser des variables d’environnement

Les informations telles que :

* clés API;
* chaînes de connexion;
* secrets;
* URLs des services;
* paramètres d’environnement;

doivent être fournies par des variables d’environnement ou un gestionnaire de secrets.

---

Protéger les informations sensibles

Les fichiers contenant des informations confidentielles ne doivent jamais être versionnés.

Les fichiers .env doivent être exclus du dépôt Git.

---

Fournir un fichier d’exemple

Chaque projet doit inclure un fichier .env.example ou équivalent permettant de comprendre les paramètres attendus sans exposer de données sensibles.

---

Documenter les paramètres

Chaque variable de configuration doit être documentée :

* nom;
* utilité;
* valeur attendue;
* caractère obligatoire ou optionnel.

---

Bonnes pratiques

✔ Centraliser la lecture de la configuration.

✔ Fournir des valeurs par défaut lorsque cela est approprié.

✔ Valider les variables au démarrage.

✔ Séparer les configurations selon les environnements.

✔ Utiliser un gestionnaire de secrets lorsque nécessaire.

✔ Limiter le nombre de paramètres.

---

Anti-patterns

Mauvais

const apiKey = "123456789";

Les informations sensibles ne doivent jamais apparaître dans le code.

---

Mauvais

Utiliser des valeurs différentes entre les développeurs sans documentation.

---

Bon

.env
DATABASE_URL=
JWT_SECRET=
OPENAI_API_KEY=

Les paramètres sont séparés du code et peuvent varier selon l’environnement.

---

Exemples

Une application doit pouvoir être déployée sur un nouvel environnement sans modification du code.

Seule la configuration doit changer.

---

Cas réel MAD DevOps

MADSuite

MADSuite utilise des variables d’environnement pour gérer :

* PostgreSQL;
* Redis;
* Stripe;
* OpenAI;
* JWT;
* URLs des applications;
* paramètres des environnements de test et de production.

Cette approche permet de déployer la même application dans plusieurs environnements sans modifier le code source.

---

Exceptions

Certaines constantes techniques (ex. : limites internes, valeurs métier stables) peuvent être définies directement dans le code lorsqu’elles ne représentent pas une configuration.

Toute exception doit être justifiée.
