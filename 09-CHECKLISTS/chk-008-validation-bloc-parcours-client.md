# CHK-008 — Validation du bloc parcours client MAD DevOps

## Objectif

Valider que le bloc **Parcours client MAD DevOps** est complet, cohérent et utilisable sur le terrain.

Cette checklist sert à confirmer que le système couvre le client du premier contact jusqu’au suivi post-livraison, sans ajouter de lourdeur inutile.

---

## Principe

```text
Comprendre avant de proposer.
Cadrer avant de promettre.
Livrer sans flou.
Apprendre sans blâme.
```

# 1. Premier contact

- [ ] Le système indique quoi faire quand un prospect arrive.
- [ ] La découverte client est couverte.
- [ ] Une phrase d’ouverture professionnelle existe.
- [ ] Le besoin réel peut être clarifié.
- [ ] Le système évite de proposer trop vite.

---

# 2. Qualification

- [ ] Un besoin flou peut être qualifié.
- [ ] La Phase 0 est prévue si nécessaire.
- [ ] Le système indique quand préparer une proposition.
- [ ] Le système permet de reporter ou refuser proprement.
- [ ] Le prix est traité après clarification suffisante.

---

# 3. Cadrage et proposition

- [ ] Le cadrage clarifie besoin, limites et succès attendu.
- [ ] La proposition décrit livrables, exclusions et prochaine action.
- [ ] Le hors périmètre est visible.
- [ ] Les conditions de démarrage sont visibles.
- [ ] La proposition reste simple et professionnelle.

---

# 4. Mandat actif

- [ ] Un mandat accepté peut devenir un projet clair.
- [ ] La fiche projet suit statut, périmètre, risques et décisions.
- [ ] Les accès requis sont visibles.
- [ ] Les blocages peuvent être documentés.
- [ ] La prochaine action est claire.

---

# 5. Suivis et communication

- [ ] Les messages de suivi couvrent les étapes principales.
- [ ] Une relance peut être envoyée sans repartir de zéro.
- [ ] Un report peut être formulé proprement.
- [ ] Une note de livraison peut être préparée.
- [ ] Les communications restent simples et humaines.

---

# 6. Livraison

- [ ] La checklist de livraison existe.
- [ ] La livraison valide le périmètre accepté.
- [ ] Les limites connues sont documentées.
- [ ] Le client sait quoi valider.
- [ ] Le suivi post-livraison est prévu.

---

# 7. Apprentissage

- [ ] Une opportunité sans suite peut être fermée proprement.
- [ ] L’apprentissage est capturé sans blâme.
- [ ] Les signaux utiles sont conservés.
- [ ] Une friction récurrente peut devenir une amélioration système.
- [ ] L’opportunité fermée ne devient pas une charge inutile.

---

# 8. Suivi du pipeline

- [ ] Les prospects actifs sont visibles.
- [ ] Les prochaines actions sont visibles.
- [ ] Les relances importantes sont visibles.
- [ ] Les mandats bloqués sont visibles.
- [ ] Les apprentissages peuvent être reliés au registre des améliorations.

---

# 9. Indexation

- [ ] Les guides du parcours client sont listés dans `SYSTEME_MAD/02-GUIDE/README.md`.
- [ ] Les playbooks du parcours client sont listés dans `SYSTEME_MAD/05-PLAY/README.md`.
- [ ] Les templates du parcours client sont listés dans `SYSTEME_MAD/07-TEMPLATES/README.md`.
- [ ] Les checklists du parcours client sont listées dans `SYSTEME_MAD/09-CHECKLISTS/README.md`.
- [ ] Le cockpit fondateur pointe vers les bons documents quand un prospect arrive.

---

# 10. Verdict

## Bloc validé

- [ ] Le bloc couvre le parcours client complet.
- [ ] Le bloc est utilisable sur le terrain.
- [ ] Le bloc reste simple pour un fondateur solo.
- [ ] Le bloc protège contre les promesses trop rapides.
- [ ] Le bloc permet de livrer et d’apprendre sans perdre le fil.

## À ajuster

- [ ] Une étape du parcours est floue.
- [ ] Un document est mal indexé.
- [ ] Un template est trop lourd.
- [ ] Une communication client manque.
- [ ] Une situation réelle n’est pas couverte.

---

## Critère de réussite

Le bloc est validé s’il permet de répondre rapidement :

```text
Qui est le client ?
Où en est-il ?
Quel besoin réel doit être compris ?
Quelle est la prochaine action ?
Qu’est-ce qui est inclus ou hors périmètre ?
Qu’est-ce qui doit être livré ?
Qu’est-ce qu’on apprend ?
```
