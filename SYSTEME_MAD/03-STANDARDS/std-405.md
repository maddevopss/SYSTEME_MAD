# STD-405 — Reprise et retour arrière

## Règle d’or

Avant de changer un système, il faut savoir quoi faire si le changement tourne mal.

---

## Objectif

Définir les principes de reprise, correction rapide et retour arrière pour les projets MAD DevOps.

L’objectif n’est pas de garantir qu’aucun problème n’arrivera. L’objectif est de réduire l’impact lorsqu’un problème survient.

---

## Pourquoi ce standard existe

Une livraison peut créer un comportement inattendu malgré les tests et validations.

Sans stratégie de reprise, l’équipe peut perdre du temps à improviser pendant que le client ou l’utilisateur subit le problème.

Une bonne stratégie de reprise permet de :

- limiter la durée d’un incident;
- protéger les données;
- réduire le stress;
- communiquer plus clairement;
- revenir rapidement à un état stable;
- apprendre de la situation.

---

## Niveau de maturité

🟡 Intermédiaire

Tout système utilisé par des clients ou utilisateurs réels doit prévoir une approche minimale de reprise.

---

## Champ d’application

Ce standard s’applique à :

- déploiements;
- migrations;
- changements de configuration;
- intégrations externes;
- jobs automatisés;
- paiements;
- exports;
- données critiques;
- fonctionnalités importantes.

---

## Règles obligatoires

### Identifier les changements risqués

Avant une livraison, identifier les éléments qui pourraient nécessiter une reprise :

- migration de données;
- changement de schéma;
- modification de configuration;
- nouveau service externe;
- nouveau workflow métier;
- changement de paiement;
- automatisation qui modifie des données.

### Prévoir une action de reprise

Pour chaque changement risqué, déterminer l’action possible :

- désactiver la fonctionnalité;
- restaurer une configuration;
- corriger rapidement;
- revenir à une version précédente;
- appliquer une migration corrective;
- bloquer temporairement une action problématique.

### Protéger les données

Toute opération qui modifie des données importantes doit être pensée avec prudence.

Lorsque nécessaire, prévoir :

- sauvegarde;
- export;
- journalisation;
- validation avant/après;
- script de correction testé.

### Garder une trace

Une reprise ou correction importante doit laisser une trace :

- problème observé;
- impact;
- action prise;
- résultat;
- apprentissage;
- action préventive future.

---

## Bonnes pratiques

✔ Déployer par petits changements.

✔ Prévoir des feature flags lorsque pertinent.

✔ Éviter les migrations irréversibles sans analyse.

✔ Tester les scripts de correction avant usage réel.

✔ Conserver les sauvegardes nécessaires.

✔ Documenter les limites connues.

✔ Faire un court post-mortem après un incident significatif.

---

## Anti-patterns

### Mauvais

Déployer une modification risquée sans plan de correction.

### Pourquoi c’est problématique

L’équipe doit improviser sous pression si un problème survient.

---

### Mauvais

Supposer qu’un retour arrière du code suffit toujours.

### Pourquoi c’est problématique

Les données, migrations et configurations peuvent rester modifiées.

---

### Mauvais

Corriger en production sans garder de trace.

### Pourquoi c’est problématique

Il devient difficile de comprendre ce qui a été changé et pourquoi.

---

## Exemple minimal de plan de reprise

```text
Changement : Nouvelle génération de facture PDF
Risque : PDF invalide ou incomplet
Détection : Test manuel + logs génération
Action de reprise : Désactiver le nouveau générateur et revenir à l’ancien template
Validation : Générer une facture test et vérifier le téléchargement
Trace : Note dans le journal de livraison
```

---

## Cas réel MAD DevOps

Pour MADSuite, les zones qui nécessitent une attention particulière sont :

- migrations PostgreSQL;
- facturation;
- paiements;
- génération PDF;
- jobs récurrents;
- notifications;
- configuration des URLs;
- modules qui modifient des données client.

---

## Exceptions

Un prototype sans utilisateurs réels peut avoir une stratégie de reprise minimale.

Toutefois, dès qu’un client ou utilisateur dépend du système, une action de reprise doit être prévue pour les changements importants.
