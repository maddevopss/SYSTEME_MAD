# CHK-005 — Qualité du parcours client

## Objectif

Cette checklist sert à valider la qualité du parcours client MAD DevOps du premier contact jusqu’au livrable final et au suivi.

Elle protège contre :

- les besoins flous;
- les promesses prématurées;
- les propositions mal cadrées;
- les projets sans décision claire;
- les livraisons incomplètes;
- les suivis oubliés.

---

## Principe directeur

Un bon parcours client doit être clair à chaque étape :

```text
Où en est le client ?
Quel problème veut-on régler ?
Quelle est la prochaine action ?
Qu’est-ce qui sera livré ?
Comment saura-t-on que c’est réussi ?
```

# 1. Avant le premier échange

## Clarté interne

- [ ] L’offre MAD DevOps est claire.
- [ ] La mission est connue.
- [ ] L’ADN MAD DevOps est respecté : aider à régler ce qui ralentit le client.
- [ ] Les offres packagées sont disponibles pour guider la discussion.
- [ ] Les limites de MAD DevOps sont comprises.

## Préparation

- [ ] Le contexte minimal du client est connu, si disponible.
- [ ] La source du contact est notée.
- [ ] Le type apparent de demande est identifié.
- [ ] Aucune solution n’est promise avant la découverte.

---

# 2. Découverte client

## Compréhension du contexte

- [ ] Le contexte actuel du client est compris.
- [ ] Le processus actuel est décrit.
- [ ] Les irritants principaux sont notés.
- [ ] Les utilisateurs concernés sont identifiés.
- [ ] Les conséquences de ne rien changer sont explorées.

## Besoin réel

- [ ] Le problème réel est distingué de la solution demandée.
- [ ] Les mots du client sont conservés dans les notes.
- [ ] Des exemples concrets passés sont demandés.
- [ ] Les impacts sont identifiés : temps, erreurs, coûts, confusion, perte d’opportunité ou autre.
- [ ] Une reformulation est faite et validée avec le client.

## Résultat attendu

- [ ] Le résultat souhaité est exprimé clairement.
- [ ] La première version utile est identifiée.
- [ ] Les critères de réussite sont observables.
- [ ] Les attentes irréalistes sont signalées rapidement.

---

# 3. Qualification

## Grille de qualification

- [ ] Le problème réel est clair.
- [ ] Les utilisateurs sont identifiés.
- [ ] Le résultat attendu est observable.
- [ ] Le hors périmètre commence à être défini.
- [ ] Le décisionnaire est identifié.
- [ ] Les contraintes principales sont connues.
- [ ] Les risques principaux sont visibles.
- [ ] Le budget ou le niveau d’effort semble réaliste.
- [ ] La prochaine action est claire.

## Verdict

Cocher un seul verdict :

- [ ] Prêt pour proposition.
- [ ] Phase 0 recommandée.
- [ ] Informations manquantes.
- [ ] À refuser ou reporter.

---

# 4. Phase 0 / cadrage préalable

À utiliser si le besoin est important mais encore flou.

- [ ] Le client comprend pourquoi une Phase 0 est recommandée.
- [ ] La Phase 0 est courte et bornée.
- [ ] Le livrable de Phase 0 est défini.
- [ ] Le périmètre de la Phase 0 est clair.
- [ ] Les éléments non inclus sont nommés.
- [ ] La décision de poursuite après Phase 0 est prévue.

Livrables possibles :

- [ ] Synthèse du besoin.
- [ ] Périmètre recommandé.
- [ ] Hors périmètre.
- [ ] Risques.
- [ ] Options de solution.
- [ ] Estimation ou feuille de route.
- [ ] Recommandation de suite.

---

# 5. Cadrage client

Avant proposition :

- [ ] Le document de cadrage est rempli si nécessaire.
- [ ] Le problème principal est écrit clairement.
- [ ] Les utilisateurs concernés sont décrits.
- [ ] La situation actuelle est documentée.
- [ ] La première version utile est définie.
- [ ] Le hors périmètre est explicite.
- [ ] Les contraintes sont notées.
- [ ] Les risques sont visibles.
- [ ] Les questions ouvertes sont listées.
- [ ] La recommandation MAD DevOps est formulée.

---

# 6. Proposition client

La proposition doit être compréhensible sans jargon.

- [ ] Le contexte est résumé.
- [ ] Le besoin identifié est clair.
- [ ] L’objectif du projet est formulé.
- [ ] La solution proposée répond au problème réel.
- [ ] Les livrables sont listés.
- [ ] Le hors périmètre est écrit.
- [ ] L’approche de réalisation est expliquée.
- [ ] Les responsabilités MAD DevOps sont précisées.
- [ ] Les responsabilités client sont précisées.
- [ ] Les hypothèses et dépendances sont listées.
- [ ] L’échéancier estimé est raisonnable.
- [ ] L’investissement ou la modalité est clair.
- [ ] Les conditions sont mentionnées.
- [ ] La prochaine action est explicite.

---

# 7. Acceptation et démarrage

Avant de commencer :

- [ ] La proposition est acceptée explicitement.
- [ ] Le périmètre accepté est clair.
- [ ] Les accès nécessaires sont fournis ou planifiés.
- [ ] Les contenus nécessaires sont fournis ou planifiés.
- [ ] Les outils de communication sont définis.
- [ ] Les jalons ou points de validation sont connus.
- [ ] Le dossier projet est créé.
- [ ] Le Starter Kit projet MAD DevOps est utilisé si pertinent.

---

# 8. Exécution

Pendant le projet :

- [ ] La TODO active est visible.
- [ ] Les décisions importantes sont documentées.
- [ ] Les changements de périmètre sont identifiés.
- [ ] Les risques sont signalés rapidement.
- [ ] Les validations client sont demandées au bon moment.
- [ ] Le parcours principal est testé régulièrement.
- [ ] Les ajouts non cadrés sont mis en phase future ou réévalués.

---

# 9. Validation avant livraison

Avant livraison :

- [ ] Le livrable correspond au périmètre accepté.
- [ ] Le parcours principal fonctionne.
- [ ] Les erreurs évidentes sont corrigées.
- [ ] Les limites connues sont documentées.
- [ ] Les instructions d’utilisation sont préparées.
- [ ] La note de livraison est prête.
- [ ] `CHK-003 — Livraison client` est passée si applicable.

---

# 10. Livraison

Au moment de livrer :

- [ ] Le client reçoit une explication claire de ce qui est livré.
- [ ] Le client reçoit les accès ou instructions nécessaires.
- [ ] Les limites connues sont mentionnées.
- [ ] Les éléments hors périmètre ne sont pas présentés comme livrés.
- [ ] La prochaine étape est proposée.
- [ ] Une confirmation de réception ou validation est demandée.

---

# 11. Suivi après livraison

Après livraison :

- [ ] Le client comprend ce qui a été livré.
- [ ] Les accès fonctionnent.
- [ ] Les questions restantes sont notées.
- [ ] Les ajustements demandés sont triés : correction, amélioration, nouveau périmètre.
- [ ] La maintenance ou la suite est clarifiée.
- [ ] Une opportunité d’amélioration est documentée si pertinente.

---

# 12. Red flags finaux

Bloquer ou ralentir si :

- [ ] Le client change constamment d’objectif.
- [ ] Le succès n’est toujours pas observable.
- [ ] Le décisionnaire est absent.
- [ ] Le client refuse de valider les livrables.
- [ ] Le client ajoute du périmètre sans réévaluer.
- [ ] Les accès ou contenus nécessaires ne sont jamais fournis.
- [ ] Le projet repose encore sur « on verra en avançant ».

---

# Verdict qualité

Choisir un verdict :

- [ ] Parcours client prêt.
- [ ] Parcours client prêt avec réserves.
- [ ] Cadrage supplémentaire requis.
- [ ] Proposition à réviser.
- [ ] Livraison à bloquer temporairement.
- [ ] Projet à refuser ou reporter.

---

## Règle finale

La qualité du parcours client se mesure à la clarté produite.

Un bon mandat doit permettre de répondre à tout moment :

```text
Quel problème règle-t-on ?
Pour qui ?
Avec quelle première version utile ?
Selon quel périmètre ?
Avec quel critère de réussite ?
Quelle est la prochaine action ?
```
