# STD-303 — Definition of Done

## Règle d’or

Une tâche n’est pas terminée quand le code fonctionne; elle est terminée quand elle peut être livrée avec confiance.

---

## Objectif

Définir ce que signifie “terminé” dans les projets MAD DevOps afin d’éviter les livraisons incomplètes, les oublis de tests, les documents non mis à jour et les corrections fragiles.

---

## Pourquoi ce standard existe

Sans définition claire du terminé, une tâche peut être considérée complète alors qu’il manque :

- les tests;
- la validation des erreurs;
- la documentation;
- la vérification sécurité;
- l’expérience utilisateur;
- la compatibilité avec l’existant;
- la préparation à la livraison.

La Definition of Done protège la qualité finale.

---

## Niveau de maturité

🟢 Fondamental

Chaque projet MAD DevOps doit avoir une définition claire du terminé.

---

## Champ d’application

Ce standard s’applique à :

- nouvelles fonctionnalités;
- corrections de bogues;
- refactorisations;
- changements de base de données;
- changements d’API;
- changements frontend;
- automatisations;
- livraisons client;
- modifications documentaires importantes.

---

## Règles obligatoires

### Critères d’acceptation respectés

La tâche doit répondre au besoin défini.

Si le besoin a changé, le changement doit être explicite.

### Tests pertinents exécutés

Les tests requis doivent être ajoutés, mis à jour ou exécutés selon le niveau de risque.

### Erreurs gérées

Les erreurs prévisibles doivent être traitées proprement.

L’utilisateur ne doit pas être exposé à une erreur brute lorsque cela peut être évité.

### Sécurité vérifiée

Toute tâche qui touche aux données, aux accès, aux paiements, à l’authentification ou aux intégrations doit inclure une vérification sécurité.

### Documentation mise à jour

La documentation doit être mise à jour lorsque le comportement, l’installation, l’architecture, la configuration ou l’usage change.

### Expérience utilisateur validée

Le parcours utilisateur doit rester compréhensible, cohérent et sans friction inutile.

### Aucun secret ajouté

Aucune clé, aucun jeton, aucun mot de passe et aucune donnée sensible ne doivent être ajoutés au dépôt.

---

## Bonnes pratiques

✔ Définir les critères de réussite avant de développer.

✔ Ajouter une checklist de fin pour les tâches complexes.

✔ Valider les impacts sur les modules voisins.

✔ Vérifier les logs et messages d’erreur.

✔ Garder une trace des décisions importantes dans une ADR.

✔ Demander une revue lorsque le risque dépasse une correction mineure.

---

## Anti-patterns

### Mauvais

Marquer une tâche terminée parce que le scénario principal fonctionne une fois localement.

### Pourquoi c’est problématique

Un test manuel unique ne prouve pas que la fonctionnalité est robuste.

---

### Mauvais

Livrer une modification sans vérifier les impacts sur les autres modules.

### Pourquoi c’est problématique

Une amélioration locale peut créer une régression ailleurs.

---

### Mauvais

Reporter systématiquement les tests et la documentation à plus tard.

### Pourquoi c’est problématique

“Plus tard” devient souvent une dette invisible.

---

## Exemple de Definition of Done minimale

Une tâche est terminée lorsque :

- le besoin est satisfait;
- les erreurs prévues sont gérées;
- les tests pertinents passent;
- la sécurité a été vérifiée;
- l’UX a été validée;
- la documentation pertinente est à jour;
- aucune donnée sensible n’a été ajoutée;
- la modification peut être relue par une autre personne.

---

## Cas réel MAD DevOps

Pour MADSuite, une fonctionnalité de facturation ne peut pas être considérée terminée si :

- les calculs ne sont pas testés;
- l’organisation n’est pas vérifiée;
- les cas d’erreur ne sont pas gérés;
- les impacts sur les PDF, paiements ou notifications ne sont pas validés;
- le parcours utilisateur reste ambigu.

---

## Exceptions

Une preuve de concept peut avoir une Definition of Done plus légère.

Toutefois, elle doit être clairement identifiée comme prototype et ne pas être confondue avec une fonctionnalité prête à livrer.
