# STD-402 — Intégration et livraison continues

## Règle d’or

Automatiser ce qui protège la qualité, pas ce qui masque le jugement.

---

## Objectif

Définir les principes d’intégration et de livraison continues pour les projets MAD DevOps.

L’objectif est de réduire les erreurs manuelles, valider les changements plus tôt et rendre les livraisons plus prévisibles.

---

## Pourquoi ce standard existe

Lorsqu’un projet grandit, les changements deviennent plus fréquents et plus risqués.

Une bonne chaîne CI/CD permet de :

- lancer les validations automatiquement;
- détecter les problèmes plus tôt;
- standardiser les étapes de livraison;
- réduire les oublis;
- améliorer la confiance avant déploiement.

---

## Niveau de maturité

🟡 Intermédiaire

Tout projet sérieux devrait avoir une automatisation minimale de validation.

---

## Champ d’application

Ce standard s’applique à :

- applications Web;
- API;
- SaaS;
- applications desktop;
- bibliothèques internes;
- scripts critiques;
- documentation générée;
- tests automatisés.

---

## Règles obligatoires

### Automatiser les validations critiques

La CI doit exécuter les validations qui protègent le projet.

Selon le contexte :

- installation des dépendances;
- lint;
- format;
- tests;
- build;
- vérification de types;
- validation de migrations;
- analyse de configuration.

### Ne pas déployer sans validation minimale

Une livraison automatisée ne doit pas contourner les vérifications importantes.

Si une validation est ignorée, la raison doit être claire.

### Séparer validation et déploiement

Valider un changement et le déployer sont deux actions différentes.

Elles peuvent être liées, mais elles ne doivent pas être confondues.

### Garder les pipelines compréhensibles

Un pipeline doit être lisible et maintenable.

Une automatisation trop complexe devient elle-même une source de risque.

---

## Bonnes pratiques

✔ Exécuter les tests avant le build lorsque pertinent.

✔ Garder les étapes courtes et nommées clairement.

✔ Échouer tôt lorsqu’une validation critique échoue.

✔ Conserver les logs de pipeline utiles.

✔ Éviter les secrets directement dans les fichiers de workflow.

✔ Documenter les variables nécessaires.

✔ Commencer simple et ajouter des étapes selon le risque réel.

---

## Anti-patterns

### Mauvais

Avoir un pipeline vert qui ne teste aucun comportement important.

### Pourquoi c’est problématique

La CI donne alors une fausse impression de sécurité.

---

### Mauvais

Rendre le pipeline si complexe que personne n’ose le modifier.

### Pourquoi c’est problématique

Une automatisation incomprise devient fragile.

---

### Mauvais

Corriger les erreurs de pipeline en désactivant les validations.

### Pourquoi c’est problématique

Cela retire précisément la protection que le pipeline devait fournir.

---

## Exemple minimal

```text
CI minimale :
1. Installer les dépendances
2. Vérifier le format ou lint
3. Exécuter les tests
4. Construire le projet
```

---

## Cas réel MAD DevOps

Pour MADSuite, la CI devrait progressivement vérifier :

- backend tests;
- frontend build;
- lint;
- tests critiques de sécurité;
- tests multi-tenant;
- migrations;
- configuration attendue;
- E2E sur les parcours principaux.

---

## Exceptions

Un prototype peut commencer sans pipeline complet.

Toutefois, avant une mise en production, les validations critiques doivent être automatisées ou documentées dans une checklist.
