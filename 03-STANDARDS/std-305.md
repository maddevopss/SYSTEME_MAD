# STD-305 — Validation avant livraison

## Règle d’or

Une livraison ne doit jamais être une surprise.

---

## Objectif

Définir les vérifications minimales à effectuer avant de livrer une fonctionnalité, une correction, une version ou un projet à un client ou à des utilisateurs.

La validation avant livraison vise à réduire les oublis, les régressions et les mauvaises surprises.

---

## Pourquoi ce standard existe

Un projet peut être presque prêt et échouer sur un détail simple :

- configuration oubliée;
- test non exécuté;
- documentation absente;
- parcours utilisateur incomplet;
- message d’erreur incompréhensible;
- environnement différent;
- donnée de démonstration oubliée;
- fonctionnalité non alignée avec le besoin initial.

La validation avant livraison agit comme dernière barrière de qualité.

---

## Niveau de maturité

🟢 Fondamental

Toute livraison client ou mise en production doit être validée selon ce standard.

---

## Champ d’application

Ce standard s’applique à :

- livraison client;
- mise en production;
- déploiement d’une nouvelle fonctionnalité;
- correction importante;
- changement de configuration;
- livraison de documentation;
- prototype présenté à un client;
- version interne utilisée comme référence.

---

## Règles obligatoires

### Vérifier le besoin initial

La livraison doit répondre au besoin qui a motivé le travail.

Si le besoin a changé, le changement doit être explicitement assumé.

### Vérifier le parcours principal

Le parcours principal doit être testé de bout en bout.

L’utilisateur doit pouvoir accomplir l’action prévue sans blocage évident.

### Vérifier les erreurs visibles

Les erreurs prévisibles doivent afficher des messages compréhensibles.

Le système ne doit pas exposer inutilement des détails techniques à l’utilisateur.

### Vérifier la configuration

Les variables, URLs, clés publiques, paramètres d’environnement et dépendances doivent être vérifiés selon l’environnement ciblé.

### Vérifier les données

Les données de test, de démonstration ou temporaires ne doivent pas être livrées par accident.

### Vérifier la documentation

La documentation doit être mise à jour lorsque la livraison change :

- l’installation;
- l’usage;
- la configuration;
- l’architecture;
- le comportement attendu;
- les limites connues.

### Vérifier la réversibilité

Lorsque pertinent, prévoir comment revenir en arrière, désactiver la fonctionnalité ou corriger rapidement si un problème apparaît.

---

## Bonnes pratiques

✔ Utiliser une checklist de livraison.

✔ Tester dans un environnement le plus proche possible de la réalité.

✔ Valider le parcours comme un utilisateur non technique.

✔ Vérifier les logs après une livraison importante.

✔ Communiquer clairement ce qui change.

✔ Mentionner les limites connues.

✔ Conserver une trace de la livraison.

---

## Anti-patterns

### Mauvais

Livrer immédiatement après le dernier changement sans revalidation.

### Pourquoi c’est problématique

Le dernier changement est souvent celui qui introduit un oubli.

---

### Mauvais

Valider uniquement la partie technique sans rejouer le parcours utilisateur.

### Pourquoi c’est problématique

Une solution techniquement correcte peut rester confuse ou inutilisable.

---

### Mauvais

Ne pas documenter ce qui a été livré.

### Pourquoi c’est problématique

Il devient difficile de comprendre plus tard ce qui a changé et pourquoi.

---

## Checklist minimale avant livraison

- [ ] Le besoin initial est respecté.
- [ ] Le parcours principal fonctionne.
- [ ] Les erreurs visibles sont compréhensibles.
- [ ] Les tests pertinents ont été exécutés.
- [ ] La configuration de l’environnement est vérifiée.
- [ ] Les données temporaires sont retirées.
- [ ] La documentation pertinente est à jour.
- [ ] Les limites connues sont identifiées.
- [ ] Un plan de correction ou retour arrière existe si nécessaire.

---

## Cas réel MAD DevOps

Pour MADSuite, une livraison doit vérifier au minimum :

- connexion;
- navigation principale;
- création d’un client;
- création ou consultation d’une facture;
- cohérence des montants affichés;
- absence de données de test visibles;
- messages d’erreur compréhensibles;
- configuration des services externes utilisés.

---

## Exceptions

Une démonstration exploratoire peut avoir une validation plus légère.

Toutefois, elle doit être présentée comme une démonstration ou un prototype, jamais comme une livraison finale.
