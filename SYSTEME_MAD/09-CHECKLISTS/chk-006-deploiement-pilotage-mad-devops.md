# CHK-006 — Déploiement du pilotage MAD DevOps

## Objectif

Valider que le système de pilotage MAD DevOps peut être utilisé sans créer une usine à gaz, une pression toxique ou un faux sentiment de contrôle.

Cette checklist protège l’intention suivante :

```text
Mesurer pour apprendre.
Piloter pour clarifier.
Améliorer sans blâmer.
```

# 1. Avant de mesurer

- [ ] Le but du pilotage est clair.
- [ ] Les métriques servent à apprendre, pas à punir.
- [ ] Les chiffres externes sont traités comme inspiration, pas comme promesses.
- [ ] Les limites du contexte MAD DevOps sont reconnues.
- [ ] La routine reste légère et utile.

---

# 2. Indicateurs V1 choisis

- [ ] Les indicateurs sont peu nombreux.
- [ ] Chaque indicateur répond à une question utile.
- [ ] Aucun indicateur n’existe seulement pour remplir un tableau.
- [ ] Les indicateurs couvrent prospects, mandats, livraisons et apprentissages.
- [ ] Les indicateurs peuvent être suivis sans lourdeur excessive.

---

# 3. Baseline interne

- [ ] Les premières valeurs servent de point de départ, pas de jugement.
- [ ] Les seuils ne sont pas copiés d’un benchmark externe.
- [ ] Les comparaisons se font avec la progression MAD DevOps dans le temps.
- [ ] Les contextes différents ne sont pas comparés mécaniquement.
- [ ] Les anomalies déclenchent une analyse, pas un blâme.

---

# 4. Routine hebdomadaire

- [ ] Un moment hebdomadaire est réservé.
- [ ] Le tableau de suivi clients est ouvert pendant la revue.
- [ ] Chaque opportunité a un statut clair.
- [ ] Chaque mandat actif a une prochaine action.
- [ ] Chaque livraison à valider est visible.
- [ ] Les opportunités sans suite sont analysées si elles contiennent un apprentissage.
- [ ] La routine se termine avec des décisions simples.

---

# 5. Garde-fous métriques

- [ ] Aucune métrique n’est utilisée comme arme.
- [ ] Aucune métrique n’est transformée en objectif rigide hors contexte.
- [ ] Aucune personne n’est classée par métrique.
- [ ] Aucun client ou mandat n’est comparé à un contexte incompatible.
- [ ] Les métriques servent à discuter du système.
- [ ] Les problèmes visibles sont traités comme des signaux utiles.

---

# 6. Lecture sans blâme

Lorsqu’un indicateur est mauvais ou inquiétant :

- [ ] Le contexte est examiné.
- [ ] Les dépendances externes sont identifiées.
- [ ] Le brief ou le périmètre est revu.
- [ ] Les décisions manquantes sont repérées.
- [ ] Les templates ou checklists faibles sont identifiés.
- [ ] Une amélioration système est proposée si nécessaire.

---

# 7. Transformation en amélioration

- [ ] Chaque friction importante produit une action concrète ou une décision de ne rien changer.
- [ ] Les améliorations sont limitées pour éviter la surcharge.
- [ ] Une amélioration système maximum est retenue par semaine.
- [ ] L’amélioration est appliquée dans un document, template, checklist, offre ou règle.
- [ ] Les apprentissages utiles sont documentés.

---

# 8. Anti-usine à gaz

- [ ] La routine ne dépasse pas la durée prévue sans raison valable.
- [ ] Le tableau reste lisible.
- [ ] Les indicateurs inutiles sont retirés.
- [ ] Les statuts trop nombreux ou confus sont simplifiés.
- [ ] La méthode aide à agir, pas seulement à documenter.

---

# 9. Verdict

## Prêt à utiliser

- [ ] Le pilotage est clair, léger et actionnable.
- [ ] Les garde-fous métriques sont respectés.
- [ ] Les documents liés sont en place.
- [ ] La première revue hebdomadaire peut être faite.

## À ajuster avant usage

- [ ] Les indicateurs sont trop nombreux.
- [ ] Les prochaines actions ne sont pas claires.
- [ ] Le tableau est trop lourd.
- [ ] Les métriques risquent de devenir punitives.
- [ ] Le système manque de lien avec les documents existants.

---

## Critère de réussite

Cette checklist est réussie si le pilotage MAD DevOps permet de répondre :

```text
Qu’est-ce qui est actif ?
Qu’est-ce qui bloque ?
Qui doit être relancé ?
Quelle livraison doit être validée ?
Quel risque doit être traité ?
Qu’est-ce qu’on a appris ?
Quelle amélioration garde-t-on ?
```
